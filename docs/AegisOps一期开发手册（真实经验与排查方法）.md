# AegisOps 一期开发手册（真实经验与排查方法）

## 1. 文档目的

本文档不是一期功能清单的重复版，而是基于 AegisOps 一期推进过程中的真实开发经历、设计取舍、联调问题和排查过程，整理出的一份开发手册。

这份手册重点回答以下问题：

1. 一期开发最容易走偏的方向问题是什么
2. 后端开发中真正难的设计点在哪里
3. 前后端对接过程中哪些地方有亮点，哪些地方最容易踩坑
4. 当项目出现“看起来像 bug，但又不完全像 bug”的问题时，应该怎么多维度排查
5. 从个人经验看，一期之后最值得保留下来的工程方法是什么

本文档更适合：

- 自己回看一期开发经验
- 给后来接手项目的人做 onboarding
- 给二期开发做方法论准备

## 2. 一期开发最重要的前提判断

从这轮开发的真实经历看，一期最重要的不是“功能写得快不快”，而是“方向判断对不对”。

如果方向判断错了，开发会出现几个很典型的问题：

- 页面越来越多，但真正能演示的闭环并没有变多
- 接口越来越多，但真实对接反而越来越难
- mock 演示看起来很完整，但切到真实后端后问题集中爆发
- 文档看起来覆盖很大，但项目实际交付能力并没有同步增长

因此，一期真正应该盯住的不是“模块面铺开率”，而是：

- 是否建立了安全底座
- 是否建立了可追踪的运维动作链路
- 是否至少打通一条完整的可演示闭环

这也是我在这轮开发里反复被验证的一个判断：

- AegisOps 一期不是做“大而全平台”
- AegisOps 一期是做“安全可追踪的最小运维控制面”

## 3. 一期最容易出现的方向问题

## 3.1 把“页面数量多”误判为“完成度高”

这是最容易出现的错觉。

项目在前端层面很快就能出现很多页面：

- 登录
- 用户
- 角色
- Secret
- 主机
- Docker
- 任务
- 审计
- 终端

但真实问题在于：

- 页面存在，不代表已经接入真实路由
- 路由存在，不代表已经接入真实后端
- 接口存在，不代表已经形成真实闭环

一期阶段里最危险的认知偏差就是：

- “代码很多了，所以项目快完成了”

实际上，一期最难的部分往往不是页面壳，而是：

- DTO 契约
- 任务化动作
- 审计闭环
- 会话生命周期
- 权限真正落到业务接口

## 3.2 把“能打开页面”误判为“前后端已经打通”

真实开发里，页面打开成功常常只能证明两件事：

1. 前端路由存在
2. 浏览器没报致命错误

但它并不能证明：

1. 页面已经请求真实后端
2. 请求已经返回符合页面预期的数据结构
3. 数据展示和动作提交已经闭环

这轮开发里非常典型的一个教训就是：

- 前端如果默认走 mock，页面看起来很流畅
- 但那并不等于项目已经进入真实联调阶段

## 3.3 把“接口 200 返回”误判为“功能闭环完成”

在控制面型产品里，接口 200 只能说明“调用成功”，不能说明“功能闭环完成”。

例如一个 Docker 容器操作接口如果只返回：

- `started: true`
- `stopped: true`
- `restarted: true`

那它可能已经能被调用，但仍然不等于项目层面的设计目标已经达到。

如果产品目标是：

- 动作可追踪
- 失败可定位
- 高风险操作可审计

那么更合理的设计就应该是：

- 动作进入任务中心
- 返回任务对象或 `taskId`
- 步骤、日志、失败原因可查

因此，一期里不能只看“接口通没通”，还要看：

- 接口是否符合控制面产品的设计目标

## 3.4 过早横向扩模块，而不是先收口闭环

从真实推进过程看，项目最容易失速的时刻，不是功能太少，而是模块太多、闭环太少。

如果在一期就急着把以下能力一起铺满：

- Registry
- 服务发布
- Nginx
- Jenkins
- 备份恢复
- 监控告警

那项目很容易变成：

- 页面很多
- 接口不少
- 但真正可演示的主链路并不稳定

所以，一期最稳的策略一定是：

- 先打通一条最小运维闭环
- 再扩展模块面

## 4. 一期真实开发经历总结

回顾这次一期开发，大体经历了几个明显阶段。

### 4.1 第一阶段：先把工程底座搭起来

这一阶段最重要的不是业务功能，而是建立最小可运行工程能力：

- 服务启动
- 配置加载
- SQLite
- GORM
- 统一响应
- 健康检查
- 默认管理员初始化

这一步的价值在于：

- 后面所有业务问题至少有稳定落点
- 不会在开发中反复怀疑“是不是服务没起来”

### 4.2 第二阶段：认证、用户、角色先打主干

这一阶段的经验是：

- 用户、角色、权限不一定要一开始就做得很复杂
- 但一定要先把基础模型与登录态打通

原因很简单：

- 没有登录态，后面的所有业务页都只能是假演示
- 没有基础角色与权限结构，后面的管理动作会越来越难补审计和授权

### 4.3 第三阶段：主机、Secret、Docker、任务页逐渐成型

这一阶段开始出现“页面越来越像平台”的感觉。

但这也是最容易产生幻觉的阶段：

- 看起来业务已经很多
- 实际上联调问题还没有真正暴露出来

因为在这个阶段里，页面很容易先走 mock 跑通，而真实后端问题会被暂时掩盖。

### 4.4 第四阶段：联调阶段暴露出真正的问题

真正有价值的经验，几乎都来自这一阶段。

这轮项目里，暴露出来的不是“服务完全跑不起来”这种粗问题，而是更典型的控制面项目问题：

- 默认 mock 导致“假联调”
- 页面能开但不一定走真实后端
- 接口返回结构和页面消费模型不一致
- 动作接口返回布尔值，但页面按任务对象处理
- 终端页面有了，但终端会话接口没有
- 路由有了，但业务接口没完全补齐

这类问题表面上看很碎，实际上它们都指向同一个核心问题：

- 项目在从“代码存在”过渡到“真实闭环”时，契约一致性不足

## 5. 后端开发中真正难的设计点

## 5.1 统一响应结构不难，真正难的是统一业务语义

后端做统一响应通常不算最难：

- `code`
- `message`
- `data`
- `traceId`

真正难的是：

- 页面到底消费数组，还是消费分页对象
- 动作到底返回布尔值，还是任务对象
- 审计结果到底是 `success/failure` 还是 `SUCCESS/FAILED`

也就是说：

- 技术上的响应统一容易做
- 业务语义上的统一更难，而且更容易在联调时出问题

## 5.2 RBAC 难点不在模型，而在“是否真正落到接口上”

用户、角色、权限这些表建出来并不难。

真正困难的地方在于：

- 业务接口有没有真正挂权限校验
- 危险动作是不是只做了前端按钮隐藏，而后端没有拦
- 角色保存时是不是把权限真实写进后端，而不是页面上勾了一堆复选框

这次一期里很典型的一个经验就是：

- RBAC 代码存在，不等于 RBAC 已经落地

只有当权限真正作用于：

- 用户管理
- 角色管理
- 主机操作
- 容器操作
- 终端访问

这些接口时，RBAC 才算真正进入工程状态。

## 5.3 Secret 模块的难点在于“看起来简单，实际牵一发动全身”

Secret 在表面上像 CRUD，但实际它影响很多模块：

- 主机 SSH
- Docker Token / TLS
- Registry
- Jenkins

所以 Secret 设计难点不只是：

- 值要加密
- 返回要脱敏

更难的是：

- 字段命名要稳定
- 引用关系要可查
- 删除前要做引用检查
- 后续模块要能统一复用

如果 Secret 这层没有收好，后面的所有远程资源接入都会反复返工。

## 5.4 任务中心的设计难点，在于决定“什么动作必须任务化”

控制面产品里，任务中心不是装饰页面。

这轮开发里我最明确的一个感受是：

- 一旦某个动作的结果需要追踪，它就应该任务化

典型例子包括：

- SSH 测试
- Docker 节点测试
- 容器启动 / 停止 / 重启
- 后续的服务发布 / 升级 / 回滚

如果这些动作只返回一个布尔值，短期开发看起来快，但很快就会遇到问题：

- 页面不知道怎么展示步骤
- 失败只能弹一句错误
- 任务中心和业务动作脱节
- 审计和动作结果难以统一

## 5.5 WebSSH 难点不在页面，而在会话生命周期

终端页很容易先写出 UI 外壳。

真正困难的地方在后端：

- 会话创建
- WebSocket 通道
- SSH session/channel 生命周期
- 页面断开后的资源释放
- 会话审计

这也是一期里非常值得保留的一个经验：

- WebSSH 不能只按“有个终端页面”来理解
- 它本质上是一个资源生命周期管理问题

## 5.6 Docker 模块难点在于“远程控制”而不是“本地调用”

Docker 节点管理如果只看 API，容易觉得就是：

- 查容器
- 看日志
- 启停容器

但真正的复杂度来自远程控制语义：

- 节点认证类型
- Token / TLS 差异
- 节点状态刷新
- 容器日志结构
- 高风险动作的确认与审计

尤其是 `TLS` 这种能力，即使在模型里预留了，也不代表就已经可用。

这提醒我一个很重要的工程原则：

- 预留字段不等于能力已经落地

## 6. 前后端对接中的亮点与收获

## 6.1 从“直连页面模型”切到“前端映射层”是一个关键亮点

一期对接中，一个非常实用的改进是：

- 前端不再直接假设后端返回的就是页面模型
- 而是在 `api.ts` 增加一层 backend -> UI 的映射

这件事的价值非常大：

- 后端字段可以渐进演进
- 前端页面不必被迫跟着所有模型细节变化
- 页面代码会更聚焦业务展示，而不是堆满兼容逻辑

这是我认为一期对接里非常值得保留的方法。

## 6.2 把 mock 改成“显式开启”，减少了大量误判

一期联调里非常关键的一次修正，就是把前端默认 mock 改成：

- 只有显式配置才启用 mock

这个改动不大，但价值非常高。

因为默认 mock 的最大问题不是“技术不好”，而是：

- 它会制造大量假进度

页面看起来正常，但实际上：

- 没有请求真实后端
- 没有暴露契约差异
- 没有暴露动作返回模型问题

所以我的经验是：

- mock 很有价值
- 但对联调分支来说，默认真实 API 更健康

## 6.3 给前端补本地代理，是联调效率非常高的一步

开发时如果没有代理，前端很容易遇到：

- 地址不一致
- 跨域
- 环境变量切换混乱

把 `/api` 代理到后端后，联调效率会明显提升，因为：

- 浏览器访问路径更统一
- 页面环境更接近真实使用方式
- 少了很多无意义的环境噪音

这类改动属于“小投入、高收益”的工程修正。

## 6.4 文档体系本身也是联调资产

这轮开发里一个明显的收获是：

- 文档不是结束后补的“说明书”
- 文档本身就是推进联调和排期的工具

尤其是以下几类文档非常有价值：

- 一期路线文档
- 联调阻塞清单
- 阶段审查报告
- 二期路线文档

它们的价值不只是记录，而是帮助团队持续回答：

- 现在到底缺什么
- 现在的问题是一期收口问题，还是二期扩展问题
- 现在该补契约，还是该加页面

## 7. 真实踩坑案例与排查办法

## 7.1 案例一：前端能打开，但登录看起来失败

表面现象：

- 页面能访问
- 登录后看起来没进入真实系统
- 页面上出现类似 `No active session` 或脚手架提示

第一反应如果是：

- “后端挂了”

那通常还不够准确。

正确排查顺序应该是：

1. 先看当前 URL 是不是目标业务路由
2. 再看前端路由表有没有把真实业务页挂进去
3. 再看页面是否默认走 mock
4. 再看浏览器实际有没有发出登录请求
5. 再直接调用后端登录接口验证真实后端是否工作
6. 最后再判断是后端问题，还是前端入口与配置问题

这轮开发里，真实结论就不是“后端坏了”，而是：

- 前端默认 mock
- 真实路由入口未完全切换
- 本地代理还没补齐

## 7.2 案例二：浏览器控制台报错，但其实不是项目代码问题

表面现象：

- 浏览器报 `runtime.lastError`
- 看起来像前端异常

这类问题如果直接改项目代码，很容易误伤。

正确排查方式是：

1. 先在仓库里全文搜索报错关键字
2. 如果仓库没有命中，优先考虑浏览器插件或运行环境噪音
3. 再结合页面功能是否真的异常做判断

这个案例的经验很重要：

- 不是所有浏览器控制台报错都来自你的业务代码

## 7.3 案例三：接口返回 200，但列表页是空的

这类问题在一期联调里非常常见。

表面现象：

- 请求成功
- 后端也返回了数据
- 页面表格却是空的

正确排查方式不是只盯网络请求，而是继续往下看：

1. 后端返回的是数组还是分页对象
2. 前端 `dataSource` 期待的是什么
3. 页面消费的是 `data`、`data.items` 还是别的字段
4. 状态码成功是否只是掩盖了 DTO 不一致

这轮项目里，很多联调问题都属于这一类。

它说明一个很现实的事实：

- 联调阶段最常见的问题不是“接口没通”
- 而是“接口通了，但契约没对齐”

## 7.4 案例四：点击动作后跳任务详情失败

表面现象：

- 页面点击“测试 SSH”或“启动容器”
- 请求成功
- 但跳转任务详情时报错或拿不到任务 ID

典型原因通常是：

- 前端把动作接口当成返回 `Task`
- 后端实际上只返回布尔结构

这个问题的价值在于，它会迫使我们去想清楚：

- 一期到底要不要把动作纳入任务中心

如果答案是“要”，那应该改的就不只是页面跳转，而是动作接口的整体设计。

## 7.5 案例五：终端页已经存在，但终端功能仍不可用

表面现象：

- `/terminal/:sessionId` 页面有了
- 页面也能打开
- 但真正从主机页进入终端失败

排查顺序应该是：

1. 前端是否真的调用了创建终端会话接口
2. 后端是否真的注册了该接口
3. 会话创建后是否有真实 session 数据
4. WebSocket 通道是否存在
5. 页面是否只是 UI 壳，而不是完整终端闭环

这个问题提醒我们：

- 页面存在不等于能力完成
- 终端链路必须从入口到会话到连接都打通

## 8. 一期推荐排查框架

## 8.1 先判断是“方向问题”还是“实现问题”

很多问题如果一开始就进代码层，很容易被带偏。

我更推荐先做第一层判断：

### 方向问题

通常表现为：

- 功能本身不在一期范围
- 一期设计目标没想清楚
- 动作是否任务化没有定论
- DTO 契约没有冻结

### 实现问题

通常表现为：

- 路由没注册
- DTO 映射不对
- 字段名不一致
- 页面状态没更新
- 接口未代理或未鉴权

如果先把这两类问题分开，排查效率会高很多。

## 8.2 再按五层模型排查

我在一期里最常用的排查顺序是下面五层：

1. 用户可见现象层
2. 前端入口与路由层
3. 浏览器请求与本地代理层
4. 后端路由与服务实现层
5. DTO / 状态 / 审计 / 任务链路层

### 第一层：用户可见现象

先不要急着看代码，先明确：

- 用户到底看到了什么
- 当前 URL 是什么
- 按钮能不能点
- 页面跳转到了哪里
- 是空白、报错、假数据，还是动作后无反馈

### 第二层：前端入口与路由

确认：

- 业务页是否真正挂在 router 里
- 是否被重定向到了别的页面
- 是否仍在默认 scaffold 入口
- 是否走了错误的页面落点

### 第三层：浏览器请求与代理

确认：

- 请求有没有真的发出
- 请求地址是不是对的
- 是否走了 `/api` 代理
- 是否仍然在 mock
- 是否有 401 / 403 / 404 / 422 / 500

### 第四层：后端路由与服务实现

确认：

- 路由是否注册
- handler 是否存在
- service 是否有真实实现
- 数据是否真正入库或查询成功

### 第五层：契约与闭环

最后确认：

- DTO 是否一致
- 页面消费模型和接口是否一致
- 动作是否纳入任务中心
- 审计是否补齐
- 闭环是否真正成立

## 8.3 用“闭环”而不是“单点成功”来判断是否完成

一期里最重要的一条判断标准是：

- 不要用单点成功判断完成度

而要问：

1. 能不能从页面发起动作
2. 动作能不能在后端执行
3. 执行结果能不能追踪
4. 失败原因能不能定位
5. 审计里能不能回看

只有这五件事串起来了，才算闭环。

## 9. 个人思考与工程方法

这一节我想保留一些比较主观、但我认为非常有价值的判断。

## 9.1 文档不是收尾动作，而是开发工具

我对这轮开发最深的一个判断是：

- 文档写得越晚，返工越多

路线文档、阻塞清单、阶段审查不是形式化产物，它们直接影响：

- 范围判断
- 排期优先级
- 联调顺序
- 是否会误判项目完成度

## 9.2 mock 很有价值，但联调阶段必须克制

mock 的价值在于：

- 能让页面先跑起来
- 能让页面设计更早暴露

但 mock 最大的问题是：

- 它会制造“项目已经差不多了”的错觉

所以我的经验是：

- 开发早期可以大胆用 mock
- 真联调阶段要默认真实 API
- mock 应该变成显式开启，而不是隐式默认

## 9.3 控制面产品的“任务”和“审计”不是附属功能

这轮开发里我越来越明确的一点是：

- 任务中心和审计日志，不是锦上添花
- 它们本身就是控制面产品的骨架

没有任务中心，动作就不可追踪。

没有审计，控制面就只是“能点按钮的后台”，还不是可控、可信、可回溯的平台。

## 9.4 后端最重要的不只是把接口写出来，而是把接口语义收口

如果接口很多，但以下问题一直反复出现：

- 有的返回数组
- 有的返回分页对象
- 有的返回布尔值
- 有的返回任务对象

那后期联调和维护成本会越来越高。

所以我现在更倾向于一个明确原则：

- 接口数量不是成熟度
- 接口语义稳定才是成熟度

## 9.5 一期之后最该保留的不是某个页面，而是一套判断方法

如果让我从一期里只保留一样东西，我不会只选某个页面或某个接口，而会保留：

- 范围控制的方法
- 联调排查的方法
- 用闭环判断完成度的方法

因为这些东西会直接决定二期开发是否会继续踩同样的坑。

## 10. 给二期开发的建议

基于一期真实经验，我对二期有几个很明确的建议：

1. 先完成一期收口，再全面进入二期
2. 二期只聚焦“服务发布闭环”
3. 前后端先冻结 DTO，再铺页面
4. 发布、升级、回滚统一任务化
5. 不要过早把 Nginx、Jenkins、监控一起拉进来

从一期经验看，最危险的节奏不是“做得慢”，而是：

- 范围开太大
- 契约不稳定
- 页面先跑，后端后补
- 最后联调压力堆到一起爆发

## 11. 最终结论

这轮一期开发真正教会我的，不是某个具体框架技巧，而是以下几件事：

1. 范围控制比功能堆积更重要
2. 页面存在不等于闭环完成
3. 接口 200 不等于业务完成
4. 控制面产品必须重视任务和审计
5. 联调阶段真正难的不是网络，而是契约、入口、状态和语义一致性

如果把这些经验沉淀下来，一期的价值就不只是“做出了一版系统”，而是：

- 做出了一套后续还能继续复用的工程方法

这也是我认为这份开发手册最值得保留的意义。
