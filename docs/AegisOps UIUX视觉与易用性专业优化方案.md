# AegisOps UI/UX 视觉与易用性专业优化方案

## 1. 文档定位

本文档从资深 UI/UX、视觉传达、企业级控制台设计与可用性治理角度，对 AegisOps 当前前端界面进行审视、拆解，并给出一套可落地的专业优化方案。

本文档不替代已有的功能排期文档，也不只讨论“界面变好看”。它更关注以下问题：

- 产品是否具备企业级运维控制台应有的专业感
- 用户是否能快速理解当前系统状态与风险优先级
- 高频操作是否足够顺畅、稳定、可回溯
- 视觉语言是否统一、克制、可信
- 页面与组件是否能支撑后续规模化迭代

## 2. 当前界面总体判断

AegisOps 当前前端已经具备企业级后台的基础骨架：

- 使用 React、Ant Design、React Query 等成熟技术栈
- 已形成侧边导航、顶部栏、页面标题、表格、抽屉、状态标签、任务日志等基础组件
- 页面结构以资源管理、任务追踪、审计、告警、系统管理为主，符合运维控制台的信息模型
- 已经出现资源工作台、任务详情、终端、审计抽屉等更贴近运维场景的界面雏形

但从专业 UI/UX 角度看，当前仍处在“功能型后台”向“企业级运维控制台”升级的中间阶段。主要问题不是页面缺少功能，而是视觉层级、信息优先级、操作闭环、状态表达和设计一致性仍需要系统治理。

一句话概括：

> 当前 AegisOps 已经具备可用后台的基础，但还需要通过设计系统化、资源上下文化、状态可视化和操作闭环化，升级为可信、专业、高效的企业级控制台。

## 3. 设计目标

### 3.1 企业化

界面应体现稳定、可信、克制、可控的企业级产品气质。

设计上避免：

- 大面积装饰性视觉
- 过度营销化表达
- 单纯追求炫酷的大屏风格
- 无明确含义的渐变、阴影、图形装饰

设计上强调：

- 清晰的信息层级
- 稳定的操作路径
- 可预期的反馈机制
- 与权限、审计、任务、告警强关联的控制台语义

### 3.2 专业化

AegisOps 面向运维、DevOps、平台工程、系统管理员等专业用户，界面应服务于判断和处理，而不是展示本身。

专业化应体现在：

- 状态可解释，而不是只有颜色
- 风险有优先级，而不是平铺展示
- 操作有上下文，而不是按钮散落
- 结果可追踪，而不是只提示“成功”
- 数据密度适中，而不是卡片堆叠或页面空旷

### 3.3 易用性强

用户应能以最少切换完成高频任务。

核心体验目标：

- 一眼知道当前是否有异常
- 两步以内定位关键资源
- 三步以内完成常见操作
- 动作结果在当前上下文内可见
- 失败时知道原因和下一步处理入口

## 4. 当前体验拆解

### 4.1 信息架构

当前导航大体分为：

- 工作台
- 资产管理
- 运维执行
- 交付发布
- 任务中心
- 审计日志
- 稳定性
- 告警配置
- 系统管理

这个架构方向是合理的，但仍有两个体验风险。

第一，业务分组偏“模块归类”，还没有充分体现用户工作流。

例如用户排查一台主机异常时，需要在主机、任务、审计、告警、终端之间切换。导航结构清楚，但跨模块任务链路仍偏散。

第二，部分命名还可以进一步企业化。

建议将导航命名从“技术对象”逐步调整为“用户认知对象”：

| 当前命名 | 建议方向 | 说明 |
| --- | --- | --- |
| 运维执行 | 运行资源 | 更容易覆盖 Docker、Nginx、执行对象 |
| 交付发布 | 应用交付 | 更贴近服务、镜像、发布链路 |
| 稳定性 | 告警中心 | 对用户更直接 |
| 告警配置 | 通知与规则 | 避免与告警中心重复 |
| 审计日志 | 操作审计 | 强化行为追踪语义 |

### 4.2 页面布局

当前页面多采用：

- PageHeader
- Card
- Toolbar
- DataTable
- Drawer

这是企业后台常见结构，优点是稳定、开发效率高、用户熟悉。

主要问题是：

- 页面之间的视觉节奏较相似，关键页面缺少明确的主次差异
- Card 使用偏多时，容易形成“块状后台”观感
- 表格、详情、动作、任务反馈之间有时分离，用户需要主动拼上下文
- 工作台统计区能展示数量，但还不够突出风险和待处理事项

优化方向：

- 保留 Ant Design 体系和现有组件基础
- 减少不必要的包裹型 Card
- 强化页面中的主工作区
- 让资源详情、动作和反馈聚合在同一上下文

### 4.3 视觉传达

当前主色为 `#0f766e`，背景为 `#f4f7f6`，整体偏稳重，适合企业运维产品。

但当前视觉系统仍有提升空间：

- 主色、状态色、文本色、边框色尚未形成完整设计令牌体系
- 状态表达主要依赖 Ant Design Badge 的默认颜色，专业感和一致性不足
- 页面标题、模块标题、表格内容、辅助文本的层级还可以更精细
- 登录页、工作台、资源页、详情页之间的品牌气质还不够统一

建议后续建立一套轻量级设计令牌：

| 类型 | 建议内容 |
| --- | --- |
| 品牌色 | 主色、悬停色、浅背景色、强调色 |
| 功能色 | 成功、警告、危险、处理中、未知 |
| 文本色 | 标题、正文、辅助、禁用、反白 |
| 边框色 | 默认、弱边框、强调边框、危险边框 |
| 背景色 | 页面背景、容器背景、弱提示背景、代码日志背景 |
| 间距 | 4、8、12、16、20、24、32 |
| 圆角 | 4、6、8，避免过度圆润 |
| 阴影 | 控制台内慎用，只在浮层、抽屉、悬停态使用 |

### 4.4 交互反馈

当前已有 message、loading、任务详情页、日志等反馈能力，基础较好。

主要问题在于反馈位置：

- 一些动作执行后直接跳转任务详情，打断当前资源上下文
- message 提示只能说明动作已提交，无法承载运维动作的持续状态
- 失败状态缺少统一的“原因、影响、下一步”表达模板

建议形成三层反馈机制：

1. 即时反馈：按钮 loading、message、行内状态变化
2. 上下文反馈：详情面板中展示最近提交任务、执行中状态、失败摘要
3. 深度反馈：进入任务详情查看步骤、日志、审计链路

## 5. 专业优化策略

### 5.1 从“页面集合”升级为“工作台体系”

企业级控制台的核心不是页面多，而是用户围绕对象持续工作。

AegisOps 的核心对象包括：

- 主机
- Docker 节点
- Nginx 节点
- Registry
- 服务定义
- 告警事件
- 任务

建议建立统一的资源工作台模式：

- 左侧为资源列表
- 右侧为资源详情面板
- 面板内包含状态、关键属性、最近任务、最近审计、主要动作
- 动作执行后在面板内产生就地反馈

现有 `HostsPage` 已经具备该模式的雏形，应作为后续页面的设计基准。

优先推广顺序：

1. 主机
2. Docker 节点
3. Nginx 节点
4. Registry
5. 服务定义

### 5.2 工作台首页从“数据概览”升级为“运营态势”

当前工作台已经有主机数、Docker 节点数、运行中任务、未处理告警，以及最近任务、告警、审计。

建议进一步调整首页信息优先级：

第一屏应回答四个问题：

- 当前系统是否健康
- 哪些异常需要立即处理
- 哪些任务正在执行或失败
- 最近是否有高风险操作

建议首页结构：

1. 顶部态势条
   - 总体健康状态
   - 未处理告警
   - 失败任务
   - 离线资源
   - 高风险审计

2. 左侧主区域
   - 待处理告警
   - 失败或超时任务
   - 异常资源

3. 右侧辅助区域
   - 最近审计
   - 最近成功任务
   - 常用入口

视觉上应让“需要处理的事项”优先于“总数量统计”。企业级运维产品的首页不是展示资产盘点，而是帮助用户判断风险。

### 5.3 状态系统专业化

运维控制台的状态非常关键。建议将状态统一为可治理的语义系统，而不是散落在各组件里的字符串映射。

建议状态分为五类：

| 类型 | 示例 | 视觉建议 |
| --- | --- | --- |
| 正常 | HEALTHY、ONLINE、SUCCESS、RESOLVED | 绿色，克制使用 |
| 处理中 | RUNNING、TESTING、DISPATCHED、PENDING | 蓝色或青色，配合动效或进度 |
| 警告 | WARNING、ACKED、CANCELED | 金色，提示需关注但不一定阻断 |
| 异常 | FAILED、OFFLINE、UNREACHABLE、TIMEOUT、CRITICAL、OPEN | 红色，必须明确原因和入口 |
| 中性 | UNKNOWN、DISABLED、DRAFT、ARCHIVED、STOPPED | 灰色，避免误导 |

状态展示规范：

- 列表中使用短标签
- 详情中使用标签加解释
- 告警中必须显示影响对象和最近触发时间
- 失败类状态必须提供查看详情、重试或关联任务入口
- 不只依赖颜色，必须有文字标签

### 5.4 操作体系分级

当前页面中按钮较多，后续应统一操作优先级。

建议每个资源上下文最多出现：

- 1 个主操作
- 2 到 3 个次操作
- 更多操作收进下拉菜单
- 高风险操作必须二次确认

主操作应由资源状态决定：

| 场景 | 主操作 |
| --- | --- |
| 主机未知或异常 | SSH 测试 |
| 主机健康 | 打开终端 |
| Docker 节点未知或离线 | 测试连接 |
| Docker 节点在线 | 查看容器 |
| 告警待处理 | 确认告警 |
| 任务失败 | 查看日志 |

这样可以减少用户判断成本，让界面主动提示“下一步最合理动作”。

### 5.5 表格体验增强

表格是 AegisOps 的主要工作界面，应保持高密度但不拥挤。

建议统一表格规范：

- 第一列为对象主信息，包含名称和辅助标识
- 第二列优先放状态
- 中间列放关键属性
- 末列放操作
- 时间字段统一显示相对时间或标准时间，避免格式混乱
- 空值统一为 `--`
- 搜索、筛选、刷新、批量操作位置固定
- 行点击用于选中资源，行内按钮用于明确动作

建议为重点页面补充：

- 状态筛选
- 标签筛选
- 最近更新时间排序
- 当前选中行高亮
- URL 保留筛选和选中状态

### 5.6 表单与抽屉体验治理

当前新增、编辑使用抽屉是正确方向，适合企业后台。

建议统一表单规范：

- 抽屉宽度按表单复杂度分为 480、640、760
- 必填项靠前
- 高风险配置项增加说明
- 默认值尽量合理，例如 SSH 端口默认为 22
- 输入错误直接落到字段下方
- 保存成功后保持当前上下文，不强制跳页
- 编辑资源时标题显示对象名称，例如 `编辑主机：prod-web-01`

对于凭证、终端、通知通道等敏感场景，应补充：

- 明确的密钥保护提示
- 密码字段不可默认回显
- 测试连接按钮
- 保存前校验
- 失败时展示具体失败原因

### 5.7 空状态与异常状态专业化

当前已有 EmptyState 和 ErrorState，建议进一步标准化文案。

空状态应回答：

- 当前为什么没有数据
- 用户可以做什么
- 是否需要权限或前置配置

示例：

- 主机空状态：`还没有主机资产`，说明：`绑定 SSH 凭证后，即可将主机接入控制台。`
- 告警空状态：`暂无待处理告警`，说明：`当前没有需要人工确认的告警事件。`
- 审计空状态：`暂无审计记录`，说明：`用户操作和系统动作会在这里形成可追溯记录。`

异常状态应回答：

- 出错位置
- 原因摘要
- traceId 或请求 ID
- 重试入口
- 是否可联系管理员

## 6. 关键页面优化方案

### 6.1 登录页

当前登录页简洁可用，但企业品牌感不足。

建议优化：

- 左侧或顶部强化 AegisOps 品牌识别
- 增加系统定位短句，例如 `企业级运维控制台`
- 登录卡片保持克制，不做营销式大图
- 初始化入口应更明确，而不是仅用说明文字
- 默认账号密码仅应在 mock 或演示环境显示，生产环境隐藏

视觉建议：

- 背景使用低对比度冷灰或浅青灰
- 卡片宽度保持 420 到 480
- 品牌图标与主色统一
- 登录按钮为唯一主视觉焦点

### 6.2 AppShell

当前壳层清晰，但可以更企业化。

建议优化：

- 侧边栏品牌区增加环境标识，如 `Demo`、`Production`
- 顶部栏增加全局搜索或快速跳转入口
- 顶部右侧增加连接状态、通知入口和用户菜单
- 面包屑保留，但层级不要过深
- 折叠菜单后图标应有 tooltip

视觉建议：

- 侧边栏宽度 240 到 256 合理
- 顶栏高度建议稳定在 56 到 64
- 内容区 padding 建议统一为 20 或 24
- 页面背景与容器边界保持轻微区分

### 6.3 工作台

建议从“统计卡片”转向“异常优先”。

改造重点：

- 将未处理告警、失败任务、异常资源放到更高优先级
- 指标卡增加状态含义，而不是只显示数量
- 最近任务区优先展示执行中、失败、超时
- 最近审计区优先展示高风险操作
- 为每个列表项提供资源入口和详情入口

### 6.4 主机与 Docker 节点

这是 AegisOps 最核心的体验试点。

建议确认并强化：

- 列表加右侧详情工作台
- 点击行选中资源
- 详情面板显示资源状态、关键属性、最近活动
- 主操作随资源状态变化
- 动作结果在面板内显示
- 任务详情仍作为深度排查页

视觉重点：

- 资源名称应是详情面板第一视觉焦点
- 状态紧贴资源名称
- 关键元信息用 2 列紧凑布局
- 最近任务与审计不超过 5 条
- 操作区保持固定位置，减少寻找成本

### 6.5 任务详情

任务详情是专业感的重要页面。

建议优化：

- 顶部展示任务状态、耗时、发起人、目标资源
- 中部展示步骤流，明确当前执行到哪里
- 日志区使用等宽字体、深色背景、错误高亮
- 失败任务提供失败原因摘要
- 提供复制任务 ID、复制日志、下载日志入口
- 关联资源、关联审计、关联告警可一键跳转

### 6.6 审计日志

审计是企业级产品的信任基础。

建议优化：

- 筛选项固定包含 actor、action、resourceType、result、时间范围
- 高风险操作使用更醒目的风险等级
- 详情抽屉展示请求摘要、变更前后、traceId
- 结果状态与任务状态视觉统一
- 支持按资源从详情面板跳转到过滤后的审计列表

### 6.7 告警中心

告警页面应以处理效率为核心。

建议优化：

- 告警列表优先按严重程度和最后触发时间排序
- 每条告警展示资源、摘要、首次触发、最近触发、次数、状态
- 告警详情中显示关联任务和审计
- 操作区明确区分确认、关闭、查看资源、查看任务
- 告警规则与通知通道应能从事件反向追溯

## 7. 设计系统建议

### 7.1 组件分层

建议将组件分为四层治理：

| 层级 | 示例 | 目标 |
| --- | --- | --- |
| 基础组件 | Button、Input、Table、Badge | 继承 Ant Design，统一主题 |
| 业务基础组件 | DataTable、PageHeader、StatusBadge、FormDrawer | 控制一致性 |
| 资源组件 | ResourceDetailPanel、ResourceActivityList | 支撑资源工作台 |
| 场景组件 | TaskTimeline、AuditDrawer、TerminalFrame | 表达运维场景 |

### 7.2 文案规范

企业级控制台文案应简洁、明确、可执行。

建议：

- 按钮使用动词加对象，例如 `新增主机`、`测试连接`
- 状态使用短词，例如 `正常`、`异常`、`执行中`
- 错误文案说明原因和下一步
- 避免模糊表达，例如 `操作失败` 应改为 `SSH 测试提交失败，请检查凭证或网络连通性`
- 页面描述不宜太长，避免占用工作区

### 7.3 可访问性与可读性

建议建立最低标准：

- 文字对比度满足常规阅读需求
- 状态不只依赖颜色
- 所有图标按钮具备 tooltip 或可读标签
- 表格行 hover、selected、disabled 状态明确
- 键盘可访问能力不低于 Ant Design 默认水平
- 日志、终端、密钥等区域使用适合长时间阅读的字体和对比度

## 8. 分阶段落地计划

### 8.1 第一阶段：视觉与组件治理

目标：统一基础观感，减少页面割裂。

建议任务：

1. 建立设计令牌文档与 Ant Design theme token 映射
2. 统一 StatusBadge 状态语义
3. 统一 PageHeader、DataTable、FormDrawer、EmptyState、ErrorState 规范
4. 调整 AppShell 间距、顶部栏、侧边栏品牌区
5. 梳理页面文案，统一按钮和状态表达

验收标准：

- 主要页面在标题、间距、表格、状态、空状态上保持一致
- 状态颜色和文字不再散落定义
- 新页面可以按组件规范快速搭建

### 8.2 第二阶段：核心资源工作台

目标：提升高频资源操作效率。

建议任务：

1. 完成主机页资源工作台体验收口
2. 完成 Docker 节点页资源工作台体验收口
3. 将任务反馈从强制跳页改为就地反馈加详情入口
4. 支持 URL 保留选中资源
5. 补充最近任务、最近审计、最近告警

验收标准：

- 用户无需离开页面即可完成资源查看、动作发起、结果确认
- 当前选中资源明确可见
- 动作结果能在当前上下文追踪

### 8.3 第三阶段：风险与告警闭环

目标：让用户更快发现和处理异常。

建议任务：

1. 工作台改为异常优先
2. 告警事件增加处理工作流
3. 任务详情强化失败原因和日志操作
4. 审计支持从资源上下文精准跳转
5. 高风险操作形成统一确认模式

验收标准：

- 首页能明确展示待处理风险
- 告警、任务、审计、资源形成可追溯链路
- 失败场景有明确下一步

### 8.4 第四阶段：企业级体验增强

目标：增强规模化使用能力。

建议任务：

1. 全局搜索或快速跳转
2. 表格筛选保存
3. 批量操作
4. 资源标签治理
5. 可配置通知与个人偏好
6. 国际化文案治理

验收标准：

- 中大型资源规模下仍可快速定位对象
- 个人和团队使用体验更稳定
- 产品具备更成熟的企业级交付形态

## 9. 优先级建议

建议按投入产出比排序：

| 优先级 | 优化项 | 价值 |
| --- | --- | --- |
| P0 | 统一状态系统 | 直接提升专业感和可判断性 |
| P0 | 主机、Docker 资源工作台 | 直接改善核心操作链路 |
| P0 | 工作台异常优先 | 提升首页价值 |
| P1 | AppShell 与视觉令牌 | 提升整体企业气质 |
| P1 | 任务详情失败反馈 | 提升排障效率 |
| P1 | 审计与资源上下文联动 | 提升可信度 |
| P2 | 全局搜索与筛选保存 | 提升规模化效率 |
| P2 | 批量操作与个性化配置 | 面向成熟企业客户 |

## 10. 成功指标

建议用以下指标衡量优化效果：

### 10.1 效率指标

- 从首页进入异常资源详情的点击次数
- 完成一次主机 SSH 测试的页面跳转次数
- 从失败任务定位到关联资源的耗时
- 从告警进入处理动作的点击次数

### 10.2 可用性指标

- 新用户能否在 5 分钟内理解导航结构
- 用户能否准确区分正常、警告、异常、处理中状态
- 失败操作后用户是否知道下一步该做什么
- 空状态是否能引导用户完成首个配置

### 10.3 视觉一致性指标

- 主要页面是否使用统一间距和标题结构
- 状态标签是否来自统一映射
- 表格列结构是否符合规范
- 抽屉、确认框、错误状态是否一致

## 11. 最终建议

AegisOps 的 UI/UX 优化不建议走“视觉大改版”路线，而应采用企业级控制台更稳妥的演进方式：

1. 先统一设计系统和状态语义
2. 再把核心资源页升级为工作台模式
3. 然后强化工作台、告警、任务、审计之间的闭环
4. 最后补充全局搜索、筛选保存、批量操作等规模化能力

这样做的好处是：

- 不推翻现有前端代码结构
- 能持续复用 Ant Design 和已有组件
- 每一阶段都有明确用户价值
- 视觉专业度和操作效率能同步提升
- 更符合企业级产品渐进式成熟的路径

最终目标不是让 AegisOps 看起来“更炫”，而是让它在真实运维场景中更可信、更稳定、更高效，让用户打开系统后能快速判断风险、定位对象、执行动作并追踪结果。
