# AegisOps 阶段审查报告（一期完成度与二期建议）

## 1. 文档目的

本文档用于基于当前仓库实际代码、已接入页面、后端路由与联调现状，对 AegisOps 当前阶段做一次独立审查，重点回答以下问题：

1. 后端是否已经按一期文档规划实现完成
2. 是否需要进入第二期开发
3. 前端当前真实完成度如何
4. 下一阶段最合理的推进顺序是什么

本文档以当前仓库代码现状为准，不以理想规划或历史描述为准。

## 2. 总体结论

当前项目不能认定为“已按文档规划完全实现”。

更准确的判断是：

- 一期核心工程骨架已经建立
- 认证、用户、角色、Secret、主机、任务、Docker 等主干模块已经有可运行实现
- 前端真实业务路由已经接通，且不再默认停留在 mock 演示模式
- 但一期文档中要求的若干关键闭环仍未收口，因此当前状态更接近：
  - `一期主干已完成`
  - `一期收口未完成`
  - `二期开发确定需要，但不建议跳过一期收口直接进入二期`

## 3. 后端审查结论

### 3.1 已经具备的一期后端能力

当前后端已经具备以下较明确的一期能力：

- 工程底座
  - Gin 服务、健康检查、就绪检查、统一响应结构、中间件链路已经建立
- 认证能力
  - 自动初始化管理员
  - 登录、刷新 token、退出、获取当前用户已经实现
- 系统管理基础能力
  - 用户 CRUD
  - 角色 CRUD
  - 权限列表与权限创建
- Secret 模块
  - Secret CRUD 已存在
  - 结合服务层设计，Secret 已按“密文存储、脱敏返回”方向实现
- 主机模块
  - 主机 CRUD
  - SSH 连通性测试
- 任务中心基础
  - 任务、任务步骤、任务日志模型和查询能力已存在
- Docker 模块
  - Docker 节点 CRUD
  - 节点连通性测试
  - 容器列表、日志、启动、停止、重启

因此，从“后端是否完全空白”这个角度看，答案显然是否定的。后端已经具备比较清晰的一期主干结构。

### 3.2 后端尚未完成的一期关键项

虽然一期主模块大多已经出现，但以下关键能力仍未达到一期验收口径：

#### 3.2.1 Dashboard 接口未真正落地

一期文档将 Dashboard 基础统计列为保留能力，并要求存在：

- `GET /api/dashboard/summary`

但当前路由注册中未看到 `dashboard` 相关 handler 接入，说明前端预留的 Dashboard 真实后端仍未落地。

这意味着：

- 一期工作台首页无法基于真实后端完成闭环

#### 3.2.2 WebSSH 会话能力未落地

一期文档明确将以下能力纳入范围：

- WebSSH 基础会话
- `POST /api/hosts/:id/terminal/sessions`
- 会话关闭和资源释放

但当前主机 handler 只提供了：

- 主机 CRUD
- `test-ssh`

没有终端会话创建、终端会话查询、WebSocket 通道等真实后端接口。

这意味着：

- 一期“打开主机终端”的核心闭环仍未完成

#### 3.2.3 RBAC 还没有真正落到后端业务路由

当前仓库中已经存在：

- `internal/rbac/service.go`
- `internal/rbac/middleware.go`

但在主路由注册中，`rbacService` 只是创建后未实际挂载到资源路由。

这意味着当前更接近：

- 已有认证
- 已有用户角色权限数据结构
- 但“细粒度权限控制真正保护业务接口”尚未完整落地

因此，一期文档中关于：

- 未登录返回 401
- 无权限返回 403
- 普通用户不能访问敏感资源

还不能认定为已经完整验收。

#### 3.2.4 审计覆盖范围还不够完整

当前确认已接入审计的动作主要集中在：

- 认证
- 用户
- 角色
- 权限创建

但从 handler 检查结果看，以下模块尚未看到同等深度的审计落点：

- Secret 新增/修改/删除
- Host 新增/修改/删除/测试
- Docker 节点新增/修改/删除/测试
- Docker 容器动作

而一期文档明确要求关键动作可追踪、危险操作可审计。

因此当前只能认定：

- 审计机制已建立
- 审计覆盖未达一期完整要求

#### 3.2.5 动作接口还未形成“任务化闭环”

一期文档建议长耗时动作进入任务中心，并要求：

- 长耗时操作返回 taskId
- 任务失败可追踪步骤和错误原因

但当前很多动作接口仍直接返回：

- `connected: true`
- `started: true`
- `stopped: true`
- `restarted: true`

这意味着：

- 任务模型和任务页有了
- 但很多运维动作尚未真正纳入任务中心闭环

#### 3.2.6 Docker TLS 仍处于预留状态

当前 Docker 服务中，若 `authType == TLS`，会直接返回“保留但未启用”的错误。

这说明：

- Docker 节点接入能力是有的
- 但 TLS 认证链路尚未完成实装

### 3.3 后端是否需要二期开发

需要，而且是确定需要。

但要区分两个层次：

1. 一期收口
2. 二期扩展

当前后端真正缺的，不只是二期内容，还包括一期剩余收口项。建议不要把“一期未完成”误判成“已经可以进入二期开发”。

更合理的阶段判断是：

- 当前仍需完成一期收口
- 一期收口后进入二期

### 3.4 二期后端建议范围

结合一期文档原始规划，二期建议优先补以下闭环：

- Registry 管理
- 服务定义
- 服务实例
- 发布任务
- 发布失败补偿
- 服务版本
- 简单回滚

不建议在当前阶段直接把重心切到：

- Nginx 配置管理
- Jenkins 集成
- 备份恢复
- 指标监控

这些更适合作为后续阶段，而不是跳过当前缺口直接推进。

## 4. 前端审查结论

### 4.1 前端当前已达到的真实状态

当前前端与之前“只有 scaffold 占位页”的状态已经不同，真实情况是：

- 真实路由已经接通
- 登录链路已能走真实后端
- 本地开发代理已配置
- 默认不再强制走 mock
- 用户、角色、主机、凭证、Docker、任务、审计等页面都已接入真实业务路由

也就是说，前端目前已经不是“静态壳子”，而是进入了：

- `真实页面已挂载`
- `真实 API 已开始接入`
- `部分模块仍处于半联调状态`

### 4.2 前端已经具备的能力

前端当前已经具备以下比较实在的成果：

- 应用壳层、权限感知导航、会话恢复
- 登录页、403、404
- 用户管理页
- 角色管理页
- 主机页
- Secret 页
- Docker 节点页、节点详情页
- 任务页、任务详情页
- 审计页
- 终端页路由

同时，前端也已经补上了关键联调基础：

- 默认真实 API 模式
- `/api` -> `127.0.0.1:8080` 本地代理
- 多个列表接口的分页解包
- 任务模型映射
- 登录态与后端 token 结构映射

因此，前端的当前定位不再是“从零开发”，而是：

- 页面主体已经成型
- 正在做真实接口适配与收口

### 4.3 前端尚未完成的关键项

#### 4.3.1 Dashboard 仍未真实落地

虽然代码里存在 `dashboardApi.summary()` 和 `DashboardPage`，但当前路由实际是：

- `/dashboard` 重定向到 `/system/users`

这说明：

- 工作台页尚未作为真实首页投入使用
- 一期文档中的 Dashboard 还不能算已交付

#### 4.3.2 管理员初始化仍未真实接通

当前前端在真实模式下：

- `getSetupStatus()` 直接返回 `{ initialized: true }`
- `initAdmin()` 直接返回占位结果

这意味着：

- 管理员初始化页还没有真实后端闭环

#### 4.3.3 角色权限保存仍未真实落地

角色页界面已经存在，权限勾选也有 UI，但真实保存时当前仍提交：

- `permissionIds: []`

这说明：

- 角色管理页“看起来能配权限”
- 但真实权限绑定尚未完成

#### 4.3.4 WebSSH 前端页面存在，但真实后端链路未通

前端已经具备：

- `/terminal/:sessionId` 路由
- `terminalApi.create`
- `terminalApi.detail`

但后端未提供对应接口。

因此当前真实状态是：

- 终端页面框架有了
- 终端链路在真实环境下仍无法闭环

#### 4.3.5 主机、凭证、Docker 节点模型仍存在适配层妥协

前端虽然已经开始做 DTO 映射，但还存在明显的临时性适配，例如：

- 主机保存时把 `sshUser` 硬编码为 `root`
- Docker 节点仍用 `tlsEnabled -> authType` 的简化映射
- 容器动作仍以“成功提示”处理，而不是完整任务对象

这说明当前前端已经能跑，但还没有完全进入稳定契约阶段。

### 4.4 前端是否需要第二阶段开发

需要。

但和后端一样，前端也更适合按两个阶段来理解：

1. 一期联调收口
2. 二期功能扩展

当前前端还不能说“一期 UI 已全部完成，只差二期新页面”。更准确的是：

- 一期页面面已经铺开
- 一期联调和真实闭环还没有完全做完
- 二期需要，但不应跳过现有页面的联调收口

## 5. 当前最合理的推进顺序

建议按以下顺序推进，而不是继续横向加新模块：

### 第一阶段：一期收口

优先把当前一期范围补成真实闭环：

1. Dashboard 真实接口与真实首页
2. 管理员初始化真实后端接入
3. WebSSH 会话接口与终端链路
4. RBAC 真正挂到后端业务接口
5. Secret / Host / Docker / 容器动作审计补齐
6. 动作接口统一任务化或统一返回模型
7. 角色权限真实保存

### 第二阶段：二期开发

在一期闭环稳定后进入：

1. Registry 管理
2. 服务定义
3. 服务实例
4. 服务发布
5. 服务升级
6. 服务回滚

### 第三阶段：后续增强

最后再进入：

1. Nginx 配置管理
2. Jenkins 集成
3. 备份恢复
4. 指标监控与告警

## 6. 最终判断

### 6.1 后端最终判断

后端当前不能认定为“已经按文档规划完全实现”。

可以认定为：

- 一期主干已实现大半
- 一期关键收口尚未完成
- 二期开发确定需要

### 6.2 前端最终判断

前端当前也不能认定为“已经完整实现并可进入纯扩展阶段”。

可以认定为：

- 真实页面和真实路由已经接通
- 已脱离早期 scaffold 状态
- 正处于真实 API 适配和联调收口阶段

### 6.3 项目阶段最终判断

当前项目整体最准确的阶段表述是：

- `一期主干完成`
- `一期收口未完成`
- `二期需求明确存在，但建议在一期闭环稳定后进入`

因此，项目当前最有效的推进方式不是继续横向铺新模块，而是先把一期闭环补完整，再进入二期扩展。
