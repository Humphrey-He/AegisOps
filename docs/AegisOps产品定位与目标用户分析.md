# AegisOps 产品定位与目标用户分析

## 1. 文档目的

本文档用于基于 AegisOps 当前仓库里的真实实现情况，整理项目现状、产品定位、目标用户与需求画像。

这份文档重点回答以下问题：

1. AegisOps 当前到底已经实现到了什么程度
2. 它更像一款什么类型的产品
3. 它最适合服务哪些目标受众
4. 这些目标用户通常最关心哪些问题

本文档不以理想规划或未来愿景为准，而以当前项目的实际代码、后端路由、前端页面与联调能力为准。

## 2. 当前项目现状

从当前代码结构、后端服务能力和前端控制台实现来看，AegisOps 已经不再是一个纯概念型项目，而是一个已经具备主干能力的轻量化运维控制面 MVP。

更准确地说，当前项目状态接近：

- 一期主干能力已经建立
- 多个关键模块已经形成基础可用形态
- 前后端已经进入真实联调阶段
- 但整体仍然偏一期收口阶段，还不能视为完整企业级交付版

## 3. 当前已实现的核心能力

结合当前仓库代码，可以明确判断 AegisOps 已经具备以下后端与前端能力。

### 3.1 后端已实现能力

当前后端已经明确具备以下模块：

- 工程底座
  - Gin 服务
  - 健康检查与就绪检查
  - SQLite + GORM
  - 统一响应结构
  - 请求日志与基础中间件
- 认证与基础安全
  - 默认管理员初始化
  - 登录、刷新 Token、退出登录
  - 获取当前用户
- 用户、角色、权限
  - 用户 CRUD
  - 角色 CRUD
  - 权限列表与权限创建
  - 基础 RBAC 模型与鉴权接入
- 审计日志
  - 操作审计记录
  - 审计列表与详情查询
- Secret 模块
  - Secret CRUD
  - 凭证密文存储
  - 返回时脱敏
- 主机模块
  - 主机 CRUD
  - SSH 连通性测试
- Docker 模块
  - Docker 节点 CRUD
  - 节点连通性测试
  - 容器列表
  - 容器日志
  - 容器启动、停止、重启
- 任务中心
  - 任务模型
  - 任务步骤
  - 任务日志
  - 任务列表与详情
- 终端模块
  - 终端会话创建
  - 终端会话查询
  - WebSocket 终端流
- Registry 模块
  - Registry CRUD
  - Registry 连通性测试
  - 仓库列表查询
  - Tag 列表查询
  - Manifest 查询
- 服务发布基础模块
  - 服务定义 CRUD
  - 服务实例查询
  - 服务版本查询
  - 发布记录查询
  - 服务发布、升级、回滚入口

### 3.2 前端已实现能力

当前前端控制台已经具备以下页面与业务路由：

- 登录页
- 管理员初始化页
- Dashboard
- 用户管理
- 角色管理
- Secret 管理
- 主机管理
- Docker 节点管理
- Docker 节点详情
- 任务列表
- 任务详情
- 审计日志
- Registry 管理
- 服务定义管理
- Terminal 终端页

更重要的是，前端已经不只是页面壳，而是已经建立了真实 API 映射层，能够将后端 DTO 转换为页面所需的 UI 模型。

这意味着项目已经跨过了“只有前端页面展示”的阶段，进入了“围绕真实后端能力逐步收口”的阶段。

## 4. 当前产品的真实定位

如果完全基于当前实现，不夸大、不拔高，AegisOps 更适合被定义为：

- 面向轻量化运维控制面的 DevOps MVP
- 面向自托管场景的内部运维控制台
- 面向小中型技术团队的主机与容器资源管理入口

它当前不是：

- 完整的大而全企业级 DevOps 平台
- 覆盖 CI/CD、监控、告警、网关、备份、Agent 编排的一体化平台
- 面向超大规模复杂组织结构的成熟中台

它当前更像：

- 一个安全可追踪的最小运维控制面
- 一个把主机、容器、凭证、任务、审计和服务发布入口收拢起来的控制台
- 一个为后续服务发布闭环建设打底的一期产品

## 5. 目标用户判断

结合当前实现能力，AegisOps 最适合的目标受众不是成熟大厂平台团队，而是以下几类更贴近现实开发与运维混合场景的人。

### 5.1 小中型技术团队负责人

这类用户通常有以下特征：

- 团队人数不大
- 没有专门的平台工程团队
- 业务系统已经需要多台主机和容器化运行
- 希望逐步摆脱纯手工运维

他们希望有一个足够轻量、能快速落地的控制台，而不是一个部署与维护成本都很高的大平台。

### 5.2 全栈开发者与独立开发者

这类用户经常同时承担：

- 后端开发
- 前端交付
- 服务部署
- 服务器维护
- 故障排查

他们最需要的是：

- 一个统一入口来看主机、容器、凭证和任务
- 一个不需要额外维护大量基础设施的自建运维工具

### 5.3 初创团队里的开发兼运维角色

这类用户常见于：

- 初创公司
- 小型项目组
- 内部孵化团队

他们往往没有条件引入复杂的 DevOps 平台，但已经明显感受到以下问题：

- 服务器凭证散落
- SSH 登录方式不统一
- Docker 节点状态不透明
- 服务发布过程缺少统一记录
- 出问题后追责和回溯困难

### 5.4 内部工具建设者

这类用户可能本身就在构建团队内部工具，他们关心的是：

- 是否可私有部署
- 是否便于二次开发
- 是否能逐步扩展成更完整的发布控制面

从当前技术选型和架构形态看，AegisOps 也比较适合被这类用户作为内部运维工具底座来继续迭代。

## 6. 目标用户的一般需求

结合这些受众的真实场景，他们通常会围绕以下几类需求来评价 AegisOps 是否有价值。

### 6.1 资产接入需求

他们通常需要：

- 录入主机
- 管理 Docker 节点
- 管理镜像仓库 Registry
- 管理 SSH、Token、TLS 等凭证
- 快速验证资源是否可连接

这类需求的核心不是“功能多”，而是“接入后能不能被统一管理和使用”。

### 6.2 安全与权限需求

当团队不再是单人运维后，就会出现以下现实需求：

- 不是所有人都应该直接拿到服务器凭证
- 不同角色应该只能做不同操作
- 敏感动作需要有可回看的记录

因此，他们需要：

- 登录鉴权
- 用户与角色管理
- 基础权限控制
- 操作审计

### 6.3 日常运维动作需求

他们日常最常见的动作往往不是复杂编排，而是这些高频操作：

- 测试 SSH 连通性
- 查看主机或节点状态
- 浏览容器列表
- 查看容器日志
- 启动、停止、重启容器
- 打开终端进入主机排障

这类需求强调的是：

- 快速
- 统一入口
- 少切工具
- 出问题时能立刻定位

### 6.4 发布与版本管理需求

随着项目进入容器化交付阶段，用户会自然提出：

- 服务定义统一管理
- 镜像与版本可追踪
- 发布动作可发起
- 升级与回滚可执行
- 发布过程可记录

这也是 AegisOps 二期最自然的增长方向，因为当前项目已经有了服务定义、Registry、任务和 Docker 节点这些基础拼图。

### 6.5 排障与追踪需求

这类用户通常非常在意：

- 操作失败后能不能知道失败原因
- 发布动作能不能看到步骤
- 是否能回看是谁做了什么
- 能不能从任务和审计里追到完整链路

这意味着他们并不只需要“按钮能点”，而需要：

- 任务可追踪
- 审计可回看
- 动作有上下文

## 7. 当前最适合服务的使用场景

从当前实现情况看，AegisOps 最适合优先服务以下场景：

### 7.1 小团队自建服务器与 Docker 节点管理

适合：

- 把主机和 Docker 节点统一录入
- 测试连接状态
- 看容器和日志
- 做基础容器动作控制

### 7.2 研发团队内部的轻量运维台

适合：

- 给开发、测试、运维共享一个受控入口
- 避免大家直接靠命令行和口口相传维护环境
- 用用户、角色、审计建立最小管理秩序

### 7.3 服务发布闭环建设前的基础控制面

适合：

- 先把 Registry、服务定义、节点和任务中心接起来
- 再逐步建设发布、升级、回滚能力

这也是当前项目最合理的定位方式之一：不是一次做完整平台，而是先做一块真正可用的控制面底座。

## 8. 当前阶段不适合承诺的能力

为了避免产品定位失真，也需要明确当前不适合对外夸大承诺的部分：

- 大规模企业级多环境编排
- 完整 CI/CD 流水线整合
- 复杂审批流
- 多租户与细颗粒度组织隔离
- 完整监控、告警、备份恢复体系
- 面向海量节点的大规模调度与 Agent 架构

当前阶段如果对外表述过大，很容易造成期望失真，也会让产品路线判断再次偏离一期真实能力。

## 9. 产品定位结论

基于当前代码实现与联调状态，AegisOps 最贴近现实的产品定位可以总结为：

- 一款面向小中型技术团队、自托管场景的轻量化运维控制面
- 一款帮助团队统一主机、Docker、Secret、任务、审计与服务定义管理入口的内部工具型产品
- 一款以安全、可追踪和可扩展为目标，为后续服务发布闭环建设打底的 DevOps MVP

如果继续沿着当前路线推进，AegisOps 最有价值的方向不是变成“大而全平台”，而是继续强化：

- 真实运维动作闭环
- 任务与审计追踪能力
- 服务发布、升级、回滚的可控交付链路

这将比单纯增加更多页面或堆更多模块，更符合它当前的产品基础与用户价值。
