# AegisOps 企业级 UI 优化方向建议

## 1. 文档目的

本文档基于当前 AegisOps 一期前端代码现状，参考企业级控制台常见模式，提出一个聚焦、可落地的 UI 与页面功能优化方向。

本文档只聚焦一条主方向，不做大而全的界面改版清单，目标是让后续前端开发可以直接拆任务推进。

## 2. 建议只做一条主方向

建议优先把 AegisOps 的资源类页面升级为：

- `资源工作台模式`
- 即：`主列表 + 右侧详情面板 + 就地动作反馈`

这条方向优先落在以下两个页面：

1. `frontend/src/pages/assets/HostsPage.tsx`
2. `frontend/src/pages/docker/DockerNodesPage.tsx`

原因很简单：这两页最符合企业级运维控制台的核心路径：

- 找资源
- 看状态
- 发动作
- 看结果

## 3. 这个方向为什么值得先做

### 3.1 当前页面的问题不是“没内容”，而是“上下文被切碎”

当前前端已经有：

- 表格列表
- 新增/编辑抽屉
- 状态标签
- 任务中心
- 任务详情
- WebSSH 终端页

这些基础并不弱。

但用户在关键操作时仍然要频繁跳页：

- 在主机页看完列表后，要点按钮才知道动作结果
- 做完 `SSH 测试` 后直接跳到任务详情
- 想判断资源最近发生过什么，还要再去任务中心或审计页找
- Docker 节点、容器、任务反馈之间也缺少稳定的就地上下文

这会让页面更像“多个功能页并排摆放”，而不是一个企业级控制台。

### 3.2 企业级应用的核心，不是按钮多，而是“动作围绕对象展开”

成熟的企业级控制台通常强调一件事：

- 用户围绕一个资源对象持续工作，而不是在多个页面之间来回打断

对 AegisOps 来说，这个对象就是：

- 主机
- Docker 节点

所以界面重点不应该只是继续加按钮，而应该把资源的状态、详情、动作、结果，收回到同一个操作上下文里。

## 4. 参考的企业级模式

这条方向主要参考了三个官方模式：

1. AWS Cloudscape 的 Split view
   - 资源列表与上下文详情面板配合
   - 适合资源识别、监控、排障
   - 官方文档明确指出，它适用于“快速浏览或比较资源详情”，并且详情面板不应替代完整详情页

2. Ant Design 的 Data Display / Data List
   - 表格适合结构化数据的展示、筛选、排序、分页和操作
   - 强调信息重要级、操作频率和关联程度的编排

3. Grafana 的 Drilldown 思路
   - 通过上下文内的逐层查看，而不是让用户一开始就写查询或频繁跳页
   - 对运维、监控、排障类界面很有参考价值

参考链接：

- [Cloudscape Split view](https://cloudscape.design/patterns/resource-management/view/split-view/)
- [Ant Design Data Display](https://ant.design/docs/spec/data-display/?locale=en-US)
- [Grafana Drilldown](https://grafana.com/docs/grafana/latest/visualizations/simplified-exploration/)

## 5. 面向 AegisOps 的具体设计方向

### 5.1 页面布局改造

以桌面端为主，主机页和 Docker 节点页改为双栏工作台：

1. 左侧：资源主列表
   - 保留现有 `DataTable`
   - 保留搜索
   - 保留新增入口

2. 右侧：资源详情面板
   - 默认关闭
   - 点击表格行后自动展开
   - 切换行时更新为当前选中资源

3. 详情面板不是新页面
   - 它是“当前页内的上下文查看区”
   - 完整详情页仍然可以保留，用于更深层分析

### 5.2 详情面板建议结构

建议统一成三个区块，信息量控制在用户一眼能扫完的范围内。

#### 区块 A：资源概览

主机页建议展示：

- 主机名
- 地址与端口
- 当前状态
- 最近检测时间
- 绑定凭证
- 标签
- 备注

Docker 节点页建议展示：

- 节点名
- Endpoint
- TLS 状态
- 当前状态
- 容器数
- 最近检测时间
- 备注

#### 区块 B：最近活动

每个资源展示最近 3 到 5 条活动：

- 最近任务
- 最近审计

这部分的作用不是替代任务中心，而是让用户在当前资源上下文里快速判断：

- 刚刚谁动过它
- 上次检测是否成功
- 最近是不是发生过失败动作

#### 区块 C：动作区

主机页动作建议：

- `SSH 测试`
- `打开终端`
- `编辑`

Docker 节点页动作建议：

- `测试连接`
- `查看容器`
- `编辑`

动作区只保留 1 个主按钮，其他按钮作为次按钮。

例如：

- 主机状态未知时：`SSH 测试` 为主按钮
- 主机状态健康时：`打开终端` 为主按钮
- 节点离线时：`测试连接` 为主按钮

## 6. 页面功能如何一起升级

这个方向不是纯视觉优化，必须伴随功能闭环一起做。

### 6.1 动作反馈改为“就地反馈”

当前 `SSH 测试`、`测试连接` 这类动作执行后，页面跳到任务详情页。

建议改为：

1. 先保留在当前页面
2. 在详情面板中展示一张“最近提交任务卡片”
3. 卡片里显示：
   - 任务类型
   - 当前状态
   - 创建时间
   - `查看详情` 入口

这样用户不会被立刻带离当前资源页面，但仍然能继续进入任务详情做深查。

### 6.2 列表与详情建立稳定联动

建议增加以下交互：

1. 点击表格行，打开详情面板
2. 当前选中行高亮
3. 刷新页面后，如果 URL 带有选中资源参数，则恢复选中状态

建议 URL 形式：

- `/assets/hosts?selected=<hostId>`
- `/docker/nodes?selected=<nodeId>`

这样便于：

- 浏览器回退
- 复制链接给同事
- 调试固定资源

### 6.3 无需跳页也能完成一次常见操作闭环

以主机页为例，优化后用户应能在同一页完成：

1. 选中主机
2. 查看状态与绑定信息
3. 发起 `SSH 测试`
4. 看到任务提交状态
5. 判断是否继续 `打开终端`

这才是企业级运维控制台应有的基本体验。

## 7. 前端实现拆解

这条方向适合按两期落地。

### 7.1 第一期：纯前端可落地版本

目标：先把交互骨架做出来，不依赖大规模后端改造。

建议任务拆分：

1. 新增通用详情面板组件
   - 文件建议：`frontend/src/components/resource/ResourceDetailPanel.tsx`

2. 新增最近活动卡片组件
   - 文件建议：`frontend/src/components/resource/ResourceActivityList.tsx`

3. 为主机页增加：
   - 行选中状态
   - 右侧详情面板
   - 当前动作反馈卡片

4. 为 Docker 节点页增加：
   - 行选中状态
   - 右侧详情面板
   - 当前动作反馈卡片

5. 扩展样式
   - 在 `frontend/src/styles/global.css` 中增加双栏布局样式

建议新增样式类：

- `.resource-workbench`
- `.resource-list-pane`
- `.resource-detail-pane`
- `.resource-detail-section`

### 7.2 第二期：联调增强版本

目标：把详情面板从静态上下文升级成真正的资源工作台。

建议任务拆分：

1. 接入资源详情接口
2. 接入按资源过滤的最近任务
3. 接入按资源过滤的最近审计
4. 为动作类按钮接入实时状态刷新
5. 根据资源状态动态调整主按钮优先级

## 8. 对后端的最小支持诉求

为了让这条方向真正成立，后端建议至少补以下能力：

1. 资源详情接口稳定可用
   - `GET /api/hosts/:id`
   - `GET /api/docker/nodes/:id`

2. 支持按资源过滤最近任务
   - 例如：
   - `GET /api/tasks?resourceType=host&resourceId=...`
   - `GET /api/tasks?resourceType=dockerNode&resourceId=...`

3. 支持按资源过滤最近审计
   - 例如：
   - `GET /api/audits?resourceType=host&resourceId=...`
   - `GET /api/audits?resourceType=dockerNode&resourceId=...`

4. 动作接口统一返回任务对象或任务 ID
   - 这样前端可以直接在详情面板展示刚发起的动作结果

## 9. 设计边界

为了避免这条方向越做越重，建议明确边界：

1. 详情面板不替代完整详情页
2. 不在面板里塞入过多图表或超过 5 条活动
3. 不把所有按钮都做成主按钮
4. 第一阶段不做复杂拖拽布局和自定义面板配置

先把“高频动作的上下文连续性”做好，比一次性堆太多功能更重要。

## 10. 验收标准

这条优化方向是否落地成功，可以用下面几个结果判断：

### 10.1 主机页

用户可以在不离开主机页的情况下完成：

- 选中主机
- 看见当前状态与关键信息
- 发起 `SSH 测试`
- 看见测试任务状态
- 决定是否进入终端

### 10.2 Docker 节点页

用户可以在不离开节点页的情况下完成：

- 选中节点
- 看见当前状态与关键信息
- 发起 `测试连接`
- 看见测试任务状态
- 决定是否查看容器

### 10.3 整体体验

用户对资源的理解路径从：

- “先找列表，再跳页，再回来”

变成：

- “先选资源，再在当前页连续处理”

## 11. 最终建议

如果只选一个企业级 UI 优化方向，我建议不要先做“大盘更炫”或“颜色更高级”，而是优先做：

- `资源工作台模式：主列表 + 右侧详情面板 + 就地动作反馈`

这是最贴合 AegisOps 当前产品形态的一条路，原因是：

- 和现有代码结构兼容
- 能直接提升专业感
- 能明显改善操作效率
- 对主机与 Docker 这类高频资源页收益最大
- 可以逐页推广，而不是一次性重构全站

这条方向做出来之后，AegisOps 的前端气质会更接近成熟企业级运维控制台，而不只是“带按钮的数据管理后台”。
