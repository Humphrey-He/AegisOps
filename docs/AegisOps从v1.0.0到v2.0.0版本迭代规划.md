# AegisOps 从 v1.0.0 到 v2.0.0 版本迭代规划

## 1. 文档目的

本文档用于把 AegisOps 现有的二期路线、专项规划和产品分析收拢成一条清晰的版本演进主线，回答三个问题：

1. `v1.0.0` 之后到底先做什么、后做什么。
2. 每个阶段分别交付哪些功能，而不是只停留在方向描述。
3. 走到 `v2.0.0` 时，AegisOps 应该具备怎样的产品闭环和工程标准。

本文档是“版本迭代规划”，重点强调：

- 版本目标
- 功能清单
- 前后端分工
- 验收口径
- 依赖顺序

它不替代已有专项文档，而是把已有专项规划整合成一条从 `v1.0.0` 走向 `v2.0.0` 的版本路线图。

---

## 2. 当前基线：v1.0.0 已具备什么

当前仓库的 `v1.0.0` 已经不是脚手架，而是一套可本地运行、可演示、可联调的一期正式基线。核心能力已经覆盖：

- 身份与权限：管理员初始化、登录鉴权、用户/角色、RBAC、审计日志
- 资产与凭证：主机、Secret、SSH 测试、脱敏返回
- 运维执行：任务中心、任务步骤、任务日志、Web 终端
- 容器与交付：Docker 节点、Registry、服务定义、发布、升级、回滚
- 稳定性治理：通知通道、告警规则、告警事件、主机与服务健康检查
- 平台支撑：导出 API、备份 API、调度任务 API、Demo 数据、SQLite / PostgreSQL 支持
- 前端控制台：工作台、主机、凭证、Docker、Nginx、镜像仓库、服务、任务、告警、通知、审计、用户、角色、调度任务、终端等页面

但当前边界也很明确：

- 默认仍偏单机 / 轻量自托管场景
- 导出、备份、故障排查包以后端能力为主，前端入口还不完整
- 权限细粒度、密钥生命周期、后台调度、真实外部通知集成仍需继续增强
- 更严肃的生产稳定性仍需要长链路联调、真实环境验证和更清晰的验收标准

因此，`v1.0.0 -> v2.0.0` 的主线，不应再是“继续铺更多页面”，而应是把现有控制面打磨成更稳、更细、更可控的轻量生产控制面。

---

## 3. v2.0.0 目标定义

### 3.1 产品目标

到 `v2.0.0`，AegisOps 应达到以下状态：

- 适合作为个人运维平台和小团队内部运维控制台长期使用
- 核心高频链路形成闭环：接入资源 -> 发布变更 -> 健康检查 -> 告警通知 -> 回滚处理 -> 审计追踪 -> 导出备份
- 高风险操作不再只是“能点按钮”，而是具备权限、任务、审计、失败定位和回退入口
- 长耗时能力不再依赖同步请求硬跑到底，而是进入统一任务与调度体系
- Secret、通知、导出、备份等敏感能力具备更清晰的边界和治理手段

### 3.2 工程目标

到 `v2.0.0`，工程侧至少应达到：

- 后端关键模块具备稳定的单元测试与必要的集成测试
- 前后端 DTO 和页面行为不再频繁漂移
- 高风险链路有明确验收清单与演示脚本
- SQLite 默认可用，PostgreSQL 可切换，长链路具备更合理的锁与并发控制
- 文档体系从“规划文档很多”升级为“版本规划、部署、验收、排障文档能真正指导使用”

### 3.3 不以 v2.0.0 为主目标的内容

以下方向可以继续保留想象空间，但不应挤占 `v2.0.0` 主线：

- Kubernetes / 多集群编排平台
- 完整的 Prometheus / Alertmanager 替代品
- 多租户 SaaS、计费、组织级隔离
- 大规模 Agent 网格体系
- Jenkins / GitLab CI 深度流水线平台化
- 企业级 ITSM / 工单中心

## 4. 演进原则

### 4.1 先补闭环，再扩模块

优先做“已经存在的能力如何真正形成闭环”，而不是继续横向增加更多模块名词。

### 4.2 先稳后端契约，再铺前端页面

发布、回滚、健康检查、通知、导出、调度、权限范围等 DTO 与语义先收敛，再推进前端细化，否则联调成本会持续偏高。

### 4.3 高风险能力必须任务化、审计化

发布、回滚、Nginx 生效、非脱敏导出、备份下载、Secret 变更、通知测试等操作，都应同时具备：

- 权限校验
- 任务状态
- 审计记录
- 失败定位

### 4.4 保持“轻量自托管”而不是盲目平台化

`v2.0.0` 的竞争力应来自“够完整、够可控、够轻”，而不是盲目追求大而全。

## 5. 版本路线总览

| 版本 | 主题 | 核心目标 | 关键词 |
| --- | --- | --- | --- |
| `v1.1.0` | 稳定性闭环 | 让发布失败、主机离线、Nginx reload 失败真正可感知、可通知、可回看 | 健康检查、告警、通知、回滚建议 |
| `v1.2.0` | 数据带走能力 | 让配置、记录、排障现场、备份包都可以被导出和下载 | 导出、备份、故障排查包 |
| `v1.3.0` | 安全边界收口 | 让权限和敏感配置从“能用”走向“可控” | 细粒度权限、Secret 治理 |
| `v1.4.0` | 后台执行与调度 | 让长耗时动作脱离同步请求，进入统一任务与调度底座 | Worker、重试、超时、定时任务 |
| `v1.5.0` | 环境与协作增强 | 让平台从单人使用更自然地走向小团队协作和多环境运维 | 环境维度、批量操作、审批保护 |
| `v2.0.0` | 轻量生产控制面 | 收口前面所有能力，完成一次真正意义上的正式跃迁 | 闭环、稳定、可控、可验收 |

## 6. 详细版本规划

## 6.1 v1.1.0：稳定性闭环

### 版本目标

把现有“发布、Nginx、主机状态”从单纯的动作执行，升级成带有状态感知、通知触达和回滚入口的闭环链路。

### 后端功能清单

- 通知通道增强
  - Telegram 通道真实发送
  - 企业微信机器人 Webhook 真实发送
  - SMTP 邮件真实发送
  - 发送测试接口
  - 发送结果记录
- 告警规则增强
  - 基于事件类型的规则匹配
  - 基于资源范围的规则匹配
  - 告警去重 / 抑制 / 冷却时间
  - 告警与通知记录关联
- 健康检查闭环
  - 服务发布后自动探活
  - 支持 HTTP / TCP / 命令三类探活策略
  - 探活失败后标记发布失败
  - 生成回滚建议
- 事件统一化
  - `service_release_failed`
  - `service_health_check_failed`
  - `nginx_reload_failed`
  - `host_offline`
  - `host_recovered`
- 任务与审计联动
  - 告警事件可回溯到 task / release / resource
  - 通知结果可回溯到 task / alert event

### 前端功能清单

- 通知通道页面补齐
  - 新建 / 编辑 / 启停 Telegram、企业微信、邮箱通道
  - 测试发送入口
  - 最近发送结果展示
- 告警规则页面补齐
  - 规则列表
  - 事件类型筛选
  - 通知目标绑定
  - 冷却时间与启停控制
- 服务详情页增强
  - 发布记录增加健康检查状态
  - 发布记录增加通知状态
  - 发布记录增加回滚建议状态
  - 显示失败摘要
- 工作台增强
  - 未处理告警卡片
  - 最近发布失败
  - 最近主机离线
  - 最近 Nginx reload 失败
- 主机 / Nginx 页面增强
  - 最近失败原因
  - 最近一次通知结果

### 验收标准

- 服务发布成功后，能自动执行探活并写入结果
- 服务发布探活失败后，前端能看到失败摘要、告警记录、通知结果和回滚建议
- Nginx reload 失败后，能生成统一事件并可在前端查看
- 主机离线后，能被标记、告警并进入通知链路

### 本版本不重点纳入

- Prometheus / Alertmanager 深度集成
- 短信 / 电话类通知
- 默认自动回滚

---

## 6.2 v1.2.0：导出、备份与故障排查包

### 版本目标

让 AegisOps 具备“带走配置、带走记录、带走现场”的能力，减少平台只看得到、拿不走的问题。

### 后端功能清单

- 导出中心能力
  - 配置导出
  - 运行记录导出
  - 故障排查包导出
  - 导出任务记录
- 备份能力
  - SQLite 备份包生成
  - 配置快照写入
  - manifest 与 checksum
  - 恢复说明文档生成
- 故障排查包能力
  - 任务详情
  - 步骤
  - 日志
  - 关联审计
  - 关联告警
  - 关联通知
  - 资源快照
- 安全策略
  - 默认脱敏导出
  - 非脱敏导出单独权限
  - 导出清单明确标注哪些字段已脱敏

### 前端功能清单

- 新增导出中心页面
  - 配置导出
  - 记录导出
  - 排障包导出
  - 导出历史与下载入口
- 新增备份中心页面
  - 手动创建备份
  - 查看备份历史
  - 下载备份包
  - 查看校验信息与恢复说明
- 页面级导出入口
  - 服务详情页导出发布历史 / 排障包
  - Nginx 页面导出配置版本
  - 主机页面导出配置与可用性记录
  - 任务详情页导出日志与完整排障包
  - 审计页 / 告警页按筛选导出

### 验收标准

- 用户可以从 UI 直接发起一次完整排障包导出
- 默认导出不会泄露 Secret 明文
- 用户可以下载备份包并看到恢复说明
- 大型导出不阻塞请求链路，而是进入任务中心跟踪

### 本版本不重点纳入

- 对象存储归档
- 自动跨机备份同步
- 一键恢复整套系统

---

## 6.3 v1.3.0：权限细粒度与 Secret 治理

### 版本目标

把平台从“接口级 RBAC + 基础 Secret”推进到“可控的权限边界 + 可追踪的敏感配置中心”。

### 后端功能清单

- 权限点细化
  - `view / manage / operate / release / rollback / test / export`
  - 高风险操作权限单独拆分
  - 非脱敏导出权限单独拆分
- 资源范围权限
  - `ALL`
  - `GROUP`
  - `OWNER`
  - `RESOURCE_SET`
- Secret 引用治理
  - Secret 被哪些资源引用
  - 删除前依赖检查
  - 最近读取记录
  - 旋转 / 禁用 / 到期状态
- 敏感配置统一 Secret 化
  - 通知通道敏感参数迁入 Secret 中心
  - 后续扩展字段复用统一解密能力
- 审计增强
  - Secret 读取审计
  - Secret 变更审计
  - 高风险操作审计清晰化

### 前端功能清单

- 角色权限页增强
  - 更细的权限项
  - 权限范围配置器
  - 高风险操作权限提示
- Secret 页面增强
  - 引用关系面板
  - 最近使用记录
  - 旋转入口
  - 禁用 / 到期状态展示
- 权限交互增强
  - 无权限按钮不只是隐藏，还展示原因
  - 详情可见但不可操作场景清晰提示

### 验收标准

- 普通用户即使知道资源 ID，也无法越权访问不在范围内的资源
- 删除被引用 Secret 时，后端能明确拒绝并指出引用来源
- 通知类敏感字段不再以明文方式暴露给普通查看权限用户
- 非脱敏导出必须具备专门权限

### 本版本不重点纳入

- 外部 KMS / Vault 正式集成
- 完整多租户权限体系
- 复杂审批工作流

## 6.4 v1.4.0：任务调度与后台执行

### 版本目标

让长耗时动作真正进入统一调度体系，不再依赖同步 HTTP 请求直接跑到底。

### 后端功能清单

- 任务执行底座增强
  - 本地 worker
  - 队列化执行
  - 重试
  - 超时
  - 取消
  - 并发 key 控制
  - 运行中状态恢复
- 调度任务增强
  - 创建 / 编辑 / 启停 / 立即执行
  - 支持 cron 表达
  - 失败重试策略
  - 最近执行结果
- 周期任务接入
  - 主机可用性巡检
  - 服务健康检查巡检
  - 定时备份
  - 定时导出
- 重操作任务化
  - 导出
  - 备份
  - Nginx 发布 / reload
  - 服务发布 / 升级 / 回滚

### 前端功能清单

- 调度任务页面从“有页面”升级到“可配置、可运行、可回看”
  - 新建 / 编辑调度任务
  - 启停调度任务
  - 立即执行
  - 最近运行状态与失败原因
- 任务中心增强
  - 队列 / 运行 / 成功 / 失败维度
  - 任务来源区分：手工 / 系统 / 定时
  - 超时 / 重试次数展示
- 工作台增强
  - 周期任务异常卡片
  - 备份失败 / 巡检失败提示

### 验收标准

- 大型导出和备份不会阻塞前端页面请求
- 调度任务可以周期触发主机巡检或备份
- 失败任务可重试，超时任务可识别，运行中任务可取消
- 服务发布、Nginx 生效等重操作都能在任务中心追踪

### 本版本不重点纳入

- 分布式消息队列
- 多 worker 集群调度
- 完整 DAG 工作流编排

## 6.5 v1.5.0：环境与协作增强

### 版本目标

让平台从“主要适合单人使用”走向“更自然地支持小团队、多环境和高风险动作保护”。

### 后端功能清单

- 环境维度增强
  - 资源增加环境 / 项目 / 分组标签
  - 服务定义与发布记录支持环境区分
  - 资源查询按环境过滤
- 批量操作能力
  - 主机批量测试
  - Docker 节点批量巡检
  - 服务批量发布前校验
  - Nginx 节点批量配置测试
- 高风险保护
  - 发布 / 回滚 / Nginx 生效 / 非脱敏导出增加二次确认语义
  - 可选审批占位能力
- 操作模板
  - 常用发布参数模板
  - 常用导出模板
  - 常用巡检模板

### 前端功能清单

- 环境视图增强
  - 工作台支持环境切换
  - 服务 / 主机 / Nginx / 告警列表支持环境过滤
- 批量操作向导
  - 先校验再执行
  - 明确显示作用范围
  - 显示部分成功 / 部分失败结果
- 高风险交互增强
  - 发布 / 回滚 / 非脱敏导出 / Nginx 生效增加更明确的确认文案
  - 展示目标环境与影响范围
- 模板与快捷入口
  - 常用筛选
  - 常用导出配置
  - 常用发布参数

### 验收标准

- 同一平台中能较清晰地区分开发 / 测试 / 生产等环境
- 批量操作具备作用范围预览和任务结果回看
- 高风险操作更难误触，且操作上下文更清晰

### 本版本不重点纳入

- 完整 ITSM 审批中心
- 多组织 / 多租户工作空间
- 外部 CI/CD 深度编排

## 6.6 v2.0.0：轻量生产控制面正式跃迁

### 版本目标

`v2.0.0` 不是单个功能包，而是一次“收口版本”。它的目标是让前面几个版本的能力形成一套稳定、可验收、可长期维护的整体。

### 功能收口要求

- 稳定性闭环已落地
  - 发布后探活
  - 告警事件
  - 通知通道
  - 回滚建议
- 数据带走能力已落地
  - 导出中心
  - 备份中心
  - 故障排查包
- 安全边界已收口
  - 权限细粒度
  - Secret 引用治理
  - 非脱敏导出边界清晰
- 后台执行底座已落地
  - 调度任务
  - 重试 / 超时 / 取消
  - 长任务任务化
- 环境与协作能力已可用
  - 环境维度
  - 批量操作
  - 高风险动作保护

### 工程收口要求

- 核心链路具备清晰测试边界
  - 服务发布 / 升级 / 回滚
  - 通知发送
  - 健康检查
  - 导出 / 备份
  - 权限与 Secret 边界
  - 调度与任务重试
- 部署与运维文档收口
  - 部署说明
  - 升级说明
  - 备份恢复说明
  - 正式 release 验收清单
- 真实环境联调收口
  - 至少一套真实 Docker 节点验证
  - 至少一套真实 Nginx 节点验证
  - 至少一种真实通知通道验证

### v2.0.0 最终验收口径

到 `v2.0.0`，应至少能完成下面这条完整演示链路：

1. 接入主机、Secret、Docker 节点、Registry。
2. 创建服务定义并选择目标环境。
3. 发起发布任务并在任务中心追踪步骤与日志。
4. 发布后自动探活，失败时生成告警、发送通知并给出回滚建议。
5. 用户可在前端查看异常详情，并触发半自动回滚。
6. 用户可导出本次事件的排障包，并下载系统备份。
7. 整个过程均具备权限控制、任务记录、审计记录与失败定位信息。

## 8. 推荐开发顺序

建议按以下顺序推进，而不是并行乱铺：

1. `v1.1.0`
   - 先补稳定性闭环，因为它直接影响“控制面有没有真实运维价值”。
2. `v1.2.0`
   - 再补导出、备份、排障，因为它会显著提升平台长期自用价值。
3. `v1.3.0`
   - 在平台能力继续增强前，先把权限和敏感信息边界收紧。
4. `v1.4.0`
   - 等核心任务模型稳定后，再把长耗时动作全部任务化和调度化。
5. `v1.5.0`
   - 在任务、权限、环境基础较稳后，再补协作和批量能力。
6. `v2.0.0`
   - 最后以真实环境联调、测试覆盖、部署文档、正式验收为核心做统一收口。

## 9. 最终结论

从 `v1.0.0` 走向 `v2.0.0`，AegisOps 最合理的路线，不是继续堆更多模块名词，而是沿着下面这条主线演进：

- 先让发布与稳定性真正闭环
- 再让配置、记录与现场能够被带走
- 再把权限和敏感信息边界收紧
- 再把长链路能力纳入统一后台执行与调度
- 最后补齐环境、协作与正式验收能力

如果这条路线按顺序推进，那么 `v2.0.0` 的 AegisOps 会更像一个真正可长期使用的轻量生产控制面，而不只是一个“功能不少的运维项目”。
