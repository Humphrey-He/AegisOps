# AegisOps PostgreSQL 主阶段迁移方案

## 1. 背景与目标

AegisOps 当前已经完成 `v1.0.0` 基线，具备本地运行、接口联调、功能演示和继续演进的能力。现阶段默认数据库仍为 SQLite，这一选择对一期开发是合理的，因为它降低了启动门槛，便于单机开发、快速验证和演示。

但随着 AegisOps 的能力从“单机可运行”走向“持续联调、长期维护、偏生产化验证”，数据库底座需要进入新的阶段。PostgreSQL 主阶段迁移的核心，不是单纯把连接串从 SQLite 换成 PostgreSQL，而是让项目从“支持 PostgreSQL”进入“以 PostgreSQL 作为主要验证、部署与验收目标”的阶段。

本方案目标如下：

- 明确 AegisOps 从 SQLite 基线走向 PostgreSQL 主阶段的原因与边界
- 将迁移工作拆成可执行、可验收、可回滚的多个阶段
- 统一开发、测试、部署、数据迁移和回滚口径
- 降低数据库切换对现有功能、联调节奏和团队协作的冲击
- 为后续真实环境部署、备份恢复、性能验证和任务调度演进打基础

需要特别强调的是：

- 本阶段不是废弃 SQLite
- 本阶段也不是一次性完成企业级数据库治理
- 本阶段的定位是“让 PostgreSQL 成为 AegisOps 的主验证数据库和主部署推荐数据库”

---

## 2. 当前现状

结合当前仓库实现，AegisOps 的数据库现状可以概括为以下几点。

### 2.1 代码层现状

- 后端已同时接入 `sqlite` 与 `postgres` 驱动
- `internal/db/db.go` 已根据 `database.driver` 在 SQLite 与 PostgreSQL 间切换
- 启动时通过 `AutoMigrate(model.AllModels()...)` 自动迁移表结构
- README 已提供 PostgreSQL 环境变量示例
- 仓库中大部分业务代码基于 GORM，未深度耦合某一个数据库方言

这说明 PostgreSQL 并不是“未来概念”，而是已经接入，只是尚未成为默认和主阶段目标。

### 2.2 配置层现状

- 默认配置文件 [config.yaml](/E:/awesomeProject/AegisOps/configs/config.yaml) 中 `database.driver` 仍为 `sqlite`
- 默认 `dsn` 仍指向本地文件 `data/aegisops.db`
- 环境变量覆盖机制已经具备，可通过 `AEGISOPS_DATABASE_DRIVER` 与 `AEGISOPS_DATABASE_DSN` 切换数据库

这说明项目当前的标准启动路径仍偏向本地单机体验，而不是 PostgreSQL 优先。

### 2.3 测试与数据能力现状

- 仓库内大量测试仍以 SQLite 临时库作为默认测试数据库
- 导出、备份、恢复说明等能力目前仍明显以 SQLite 文件形态为主
- 备份模块对 SQLite 文件可直接打包，对 PostgreSQL 目前仅提供配置和排障上下文，不直接导出全量数据库文件
- 现阶段并未看到独立的 PostgreSQL schema 版本管理机制，主要依赖 GORM AutoMigrate

这说明“已支持 PostgreSQL”和“能把 PostgreSQL 作为主阶段数据库稳定运行”之间仍有明显差距。

### 2.4 部署形态现状

- 仓库当前部署资源较轻，`deploy/` 下主要是烟雾测试相关内容
- 尚未形成围绕 PostgreSQL 的标准化部署模板、初始化流程、备份流程和运维口径
- 当前正式文档里对 PostgreSQL 更偏向“可切换”，而非“推荐主部署方案”

因此，AegisOps 现在所处的位置更准确地说是：

```text
SQLite 是默认基线
PostgreSQL 已完成接入
但 PostgreSQL 还没有成为主阶段的默认验证与交付标准
```

---

## 3. 为什么进入 PG 阶段

PostgreSQL 主阶段迁移不是为了“技术栈看起来更正式”，而是因为 AegisOps 的当前能力形态已经开始逼近 SQLite 的阶段性上限。

### 3.1 当前功能复杂度已经超出“纯本地单文件数据库”最佳区间

AegisOps 已经包含以下核心数据域：

- 用户、角色、权限、审计
- 主机、Secret、Docker、Registry
- 服务定义、发布记录、实例状态
- Nginx 节点与配置版本
- 任务中心、步骤日志、调度记录
- 告警事件、通知记录、健康检查
- 导出任务、备份记录

这些模块叠加后，数据库已经不只是简单 CRUD 存储，而是在承担控制面状态管理、审计追踪、任务记录和稳定性闭环的职责。随着数据量、联调频次和写入并发增加，继续以 SQLite 作为主阶段数据库，会让很多“应用问题”和“数据库形态限制”混在一起。

### 3.2 PostgreSQL 更适合作为长期主验证底座

相较于 SQLite，PostgreSQL 更适合承担以下需求：

- 更稳定的并发读写能力
- 更清晰的连接池与服务端连接管理
- 更接近真实生产部署形态
- 更容易验证索引、排序、分页、事务和锁竞争行为
- 更方便后续引入独立备份、恢复、只读分析和外部运维工具

对 AegisOps 来说，PG 阶段的价值不在于“能承受超大规模”，而在于“能更真实地暴露生产型问题，并给后续演进提供更稳的底座”。

### 3.3 当前仓库已有 PG 接入基础，迁移成本可控

如果仓库完全没有 PostgreSQL 接入，现在切主阶段会是高风险动作；但当前代码已经具备以下基础：

- 驱动已接入
- 配置切换已存在
- README 已给出基本使用方式
- 业务代码大体通过 GORM 抽象访问数据库
- 部分代码已对 PostgreSQL 方言做过兼容判断

这意味着 AegisOps 已经到了“适合把 PostgreSQL 从可选项升级为主阶段项”的时间点。

### 3.4 现在进入 PG 阶段，比更晚进入成本更低

如果继续长期以 SQLite 为默认主验证路径，会出现几个后果：

- 更多功能在 SQLite 语义下继续叠加
- 导出、备份、恢复能力继续围绕 SQLite 文件思维扩展
- 更多测试默认在 SQLite 下通过，但 PostgreSQL 下问题延后暴露
- 后续再切主阶段时，回归范围更大、历史兼容问题更多

因此，当前阶段推进 PostgreSQL 主阶段迁移，属于“越早越划算”的基础设施升级。

## 4. 阶段拆分

建议把 PostgreSQL 主阶段迁移拆成五个阶段推进，而不是一次性切换。

## 4.1 阶段 0：现状校准与边界确认

目标：

- 明确 PG 阶段的范围、非目标和验收口径

本阶段重点：

- 保持 SQLite 可继续用于本地极速启动和轻量测试
- 明确 PostgreSQL 将成为主联调、主验收、主部署推荐数据库
- 盘点所有显式或隐式依赖 SQLite 文件特性的模块
- 识别当前备份、导出、恢复、测试中的 SQLite 假设

阶段出口：

- 团队对“SQLite 保留，但不再是主阶段标准”达成一致
- 形成 PostgreSQL 迁移任务清单和责任分工

## 4.2 阶段 1：开发与联调主路径切换

目标：

- 让 PostgreSQL 成为日常开发联调的优先数据库

本阶段重点：

- 提供标准 PostgreSQL 本地启动方式
- 提供推荐 DSN、库名、账号权限和初始化说明
- 以 PostgreSQL 完成后端启动、前后端联调、管理员初始化、核心页面联调
- 逐步要求新增后端能力优先在 PostgreSQL 下验证

阶段出口：

- 开发成员可以稳定用 PostgreSQL 启动 AegisOps
- 常用联调流程不再依赖 SQLite 作为唯一标准路径

## 4.3 阶段 2：核心能力兼容与数据面收口

目标：

- 解决业务功能在 PostgreSQL 下的兼容、稳定性和数据迁移问题

本阶段重点：

- 排查排序、分页、空值、大小写、默认值、事务边界等差异
- 核查告警、任务、发布、调度、导出、备份等关键模块
- 明确从 SQLite 到 PostgreSQL 的迁移建议和脚本策略
- 修正仍依赖 SQLite 文件语义的备份恢复描述

阶段出口：

- 核心业务流程可在 PostgreSQL 下稳定运行
- 迁移前后数据完整性有明确检查口径

## 4.4 阶段 3：部署、备份与验收主路径切换

目标：

- 让 PostgreSQL 成为正式部署与版本验收的主推荐方案

本阶段重点：

- 明确 PostgreSQL 生产/预发配置模板
- 建立数据库初始化、备份、恢复、版本升级流程
- 把正式验收清单扩展为 PostgreSQL 优先口径
- 补齐 PostgreSQL 相关运维说明

阶段出口：

- PostgreSQL 成为文档、部署和验收中的主路径
- SQLite 转为开发便捷方案和轻量演示保底方案

## 4.5 阶段 4：长期治理与收口

目标：

- 从“可运行”升级到“可长期维护”

本阶段重点：

- 考虑引入独立 schema migration 管理
- 补齐 PostgreSQL 备份与恢复自动化
- 补齐性能基线、索引治理和容量预估
- 把 PostgreSQL 验证纳入长期回归体系

阶段出口：

- PostgreSQL 不仅是主阶段数据库，也是可持续维护的长期底座

## 5. 配置与部署

PostgreSQL 主阶段迁移必须先统一配置与部署口径，否则团队会长期停留在“每个人自己试出来”的状态。

### 5.1 配置建议

建议保留现有配置结构不变，继续使用：

- `database.driver`
- `database.dsn`

推荐约定如下：

- 本地 SQLite 快速模式：`driver=sqlite`
- 本地/联调/预发/生产标准模式：`driver=postgres`
- 文档和脚本示例统一使用 `postgres://` DSN

建议 PostgreSQL 环境变量示例：

```powershell
$env:AEGISOPS_DATABASE_DRIVER = "postgres"
$env:AEGISOPS_DATABASE_DSN = "postgres://aegisops:replace-me@127.0.0.1:5432/aegisops?sslmode=disable"
```

### 5.2 数据库参数建议

建议至少统一以下基线：

- 独立数据库名：`aegisops`
- 独立业务账号：仅授予本库所需权限
- 非生产环境可先使用 `sslmode=disable`
- 生产环境应切到受控 SSL 配置
- 明确时区策略，建议统一使用 UTC 存储、前端展示做本地化

### 5.3 本地部署建议

建议为团队形成固定本地 PG 联调方式，至少做到：

- 一条标准启动命令
- 一份推荐初始化 SQL 或容器配置
- 一个最小联调流程

推荐本地流程：

1. 启动 PostgreSQL 实例
2. 创建 `aegisops` 数据库与业务账号
3. 配置 `AEGISOPS_DATABASE_DRIVER=postgres`
4. 配置 `AEGISOPS_DATABASE_DSN`
5. 启动后端并执行自动迁移
6. 完成管理员初始化和基础联调

### 5.4 环境分层建议

建议从现在开始把数据库环境分成三层：

- 本地开发：允许 SQLite 或 PostgreSQL，但推荐 PostgreSQL
- 联调/验收：默认 PostgreSQL
- 预发/生产：仅 PostgreSQL

这样既保留本地低门槛体验，也能明确主阶段标准。

### 5.5 部署侧注意事项

进入 PG 阶段后，部署说明中应明确增加以下内容：

- 应用启动前确保 PostgreSQL 可连接
- 数据库账号权限最小化
- 连接池参数应与 PostgreSQL 部署规模匹配
- 备份策略不能再等同于“拷贝 SQLite 文件”
- 升级前必须有数据库备份和回滚演练

## 6. 数据迁移建议

SQLite 到 PostgreSQL 的迁移，建议遵循“先验证结构，再迁移数据，再做校验”的原则，而不是直接把线上或长期使用的数据一次性灌入。

### 6.1 总体原则

- 迁移前先冻结变更窗口
- 先做一次完整 SQLite 备份
- 先在测试环境演练，再进入正式环境
- 迁移完成后做结构、数量、抽样和链路四层校验

### 6.2 建议迁移路径

建议采用以下路径：

1. 从 SQLite 导出现有关键数据
2. 在 PostgreSQL 新库上执行应用启动与 AutoMigrate
3. 通过脚本或中间导出格式导入 PostgreSQL
4. 执行业务级校验
5. 完成只读验证后再切换写流量

### 6.3 建议优先迁移的数据域

第一优先级：

- 用户、角色、权限
- Secret 元数据与引用关系
- 主机、Docker、Registry、Nginx、Service 等配置型资源
- 环境、告警规则、通知通道

第二优先级：

- 服务版本
- 发布记录
- 任务、步骤、日志
- 调度记录

第三优先级：

- 审计日志
- 告警事件
- 通知记录
- 健康检查记录
- 导出任务与备份记录

这样做的原因是：配置型资源优先迁移能保证系统尽快可用，历史记录类数据可以按重要性分批处理。

### 6.4 数据校验建议

迁移后至少做以下校验：

- 表级数量校验：核心表记录数前后一致
- 关系校验：外键语义对应的关联数据未丢失
- 关键字段校验：ID、状态、时间字段、资源引用字段正确
- 抽样校验：随机抽查用户、服务、任务、告警、发布记录
- 链路校验：登录、发布、回滚、告警、导出、备份等核心流程可跑通

### 6.5 对现有备份能力的要求

当前导出/备份模块对 PostgreSQL 的支持更偏“上下文备份”，不是完整数据库备份。因此在 PG 阶段迁移中，不能把应用内现有备份接口当作唯一恢复手段。

建议同时准备：

- 应用层导出与排障包
- PostgreSQL 官方逻辑备份
- 必要时的实例快照或存储快照

### 6.6 迁移策略建议

建议优先采用“停写迁移”而不是“边写边迁移”。

原因如下：

- 当前项目体量更适合简单可控方案
- 业务代码尚未体现双写、增量订阅或 CDC 设计
- 停写迁移更容易保证一致性和回滚可执行性

因此，主阶段迁移建议路线为：

```text
备份 SQLite
-> 停止写入
-> 导出与迁移
-> PostgreSQL 验证
-> 切换应用
-> 观察期确认
```

## 7. 测试与验收

PostgreSQL 主阶段迁移如果没有明确测试口径，很容易停留在“服务能启动”这种伪完成状态。

### 7.1 测试分层建议

建议把测试与验收拆成四层。

#### 第一层：启动与基础连接测试

- PostgreSQL 可连接
- 应用启动成功
- AutoMigrate 正常执行
- `/healthz` 与 `/readyz` 正常返回

#### 第二层：核心模块功能测试

- 登录、鉴权、管理员初始化
- 用户、角色、权限、审计
- 主机、Secret、Docker、Registry
- 服务定义、发布、升级、回滚
- Nginx 配置发布与回滚
- 任务中心、任务步骤、任务日志
- 告警、通知、健康检查
- 导出、备份、调度

#### 第三层：数据一致性测试

- SQLite 迁移前后记录数对比
- 关键业务对象关联关系检查
- 关键筛选、分页、排序结果检查
- 时间字段和状态字段抽样检查

#### 第四层：异常与恢复测试

- PostgreSQL 短暂不可达时的启动与报错表现
- 错误 DSN 或权限不足时的失败表现
- 切换失败后的 SQLite 回退验证
- 备份恢复后的基础可用性验证

### 7.2 主验收场景建议

建议至少以以下场景作为 PostgreSQL 主阶段验收口径：

1. 使用 PostgreSQL 启动全套后端服务并完成管理员初始化
2. 前端在 PostgreSQL 环境下完成完整登录与基础页面联调
3. 创建主机、Secret、Docker 节点、Registry、服务定义
4. 完成一次服务发布与一次回滚
5. 完成一次 Nginx 配置发布
6. 生成任务日志、审计日志、告警事件与通知记录
7. 完成一次导出和一次备份操作
8. 重启服务后再次验证数据可读、可写、可查询

### 7.3 验收标准建议

满足以下条件，才建议判定为“进入 PG 主阶段”：

- PostgreSQL 成为联调与验收默认数据库
- 核心业务流程在 PostgreSQL 下可重复稳定执行
- 有明确的数据迁移演练记录
- 有可执行的回滚预案
- 文档和部署说明已将 PostgreSQL 作为主推荐方案

## 8. 回滚预案

数据库主阶段切换必须自带回滚方案，否则风险会从技术问题变成交付问题。

### 8.1 回滚原则

- 先备份，再切换
- 先演练，再正式执行
- 回滚目标优先是“恢复可用”，不是“保持所有新写入都不丢”

### 8.2 推荐回滚触发条件

出现以下任一情况，应进入回滚评估：

- PostgreSQL 环境下应用无法稳定启动
- 关键业务链路无法跑通
- 数据迁移后存在明显缺失或关联断裂
- 发布、任务、告警、导出等核心模块出现系统性异常
- 观察期内数据库相关故障频繁出现且无法快速定位

### 8.3 推荐回滚路径

建议保留 SQLite 原始数据库文件及其对应配置，回滚路径如下：

1. 停止当前 PostgreSQL 写入
2. 保留 PostgreSQL 故障现场与日志
3. 恢复原 SQLite 配置
4. 指回原 SQLite 数据文件备份
5. 启动 AegisOps 并验证登录、核心资源、关键任务链路
6. 暂停 PostgreSQL 切换，进入问题复盘

### 8.4 回滚前必须准备的内容

- SQLite 原库完整备份
- PostgreSQL 切换前数据快照
- 切换执行步骤文档
- 回滚执行步骤文档
- 切换观察期负责人和值守口径

### 8.5 需要注意的现实边界

如果切换后已经在 PostgreSQL 中产生了新增写入，而随后又回滚到 SQLite，那么这部分新数据需要单独评估是否补录，不应假设能自动无损回灌。

因此，正式切换时建议：

- 选低峰窗口
- 设置短观察期
- 在观察期内限制高风险操作

---

## 9. 风险清单

PostgreSQL 主阶段迁移的主要风险建议明确列出并提前管控。

### 9.1 结构迁移风险

- 当前主要依赖 GORM AutoMigrate，缺少更细粒度的 schema 版本控制
- 不同数据库对默认值、索引、字段类型的落地可能存在差异

控制建议：

- 先在测试库完整演练
- 记录迁移前后表结构和关键索引
- 后续逐步考虑引入独立 migration 管理

### 9.2 数据兼容风险

- SQLite 与 PostgreSQL 在排序、大小写、空值、事务细节上存在差异
- 某些查询在 SQLite 下可工作，不代表在 PostgreSQL 下结果完全一致

控制建议：

- 对列表页、筛选页、排序页做专项回归
- 对关键写操作做事务与幂等性检查

### 9.3 测试口径失真风险

- 当前大量测试默认使用 SQLite，容易造成“测试通过但 PG 失败”

控制建议：

- 逐步增加 PostgreSQL 集成测试
- 至少让核心链路具备 PostgreSQL 回归用例

### 9.4 备份恢复能力不足风险

- 当前项目对 PostgreSQL 的完整备份恢复体系还未成型

控制建议：

- 把 PostgreSQL 官方备份工具纳入迁移流程
- 不把应用内备份能力当成唯一恢复手段

### 9.5 部署复杂度上升风险

- 相比 SQLite，PostgreSQL 引入了实例管理、网络、权限、备份、监控等额外成本

控制建议：

- 先在联调和预发环境标准化
- 用文档和脚本消化复杂度，而不是让每个成员自己摸索

### 9.6 回滚窗口风险

- 一旦切换后持续写入 PostgreSQL，回滚成本会快速上升

控制建议：

- 切换窗口尽量短
- 观察期内控制变更节奏
- 明确谁有权触发回滚决策

---

## 10. 里程碑建议

建议把 PostgreSQL 主阶段迁移拆成四个可管理里程碑。

### M1：PostgreSQL 联调可用

里程碑目标：

- 团队成员可按统一说明启动 PostgreSQL
- 后端可稳定连接、启动、迁移
- 前后端基础联调可跑通

完成标志：

- PostgreSQL 本地联调说明可执行
- 核心登录与基础资源管理可用

### M2：核心功能 PG 回归通过

里程碑目标：

- 核心业务链路在 PostgreSQL 下稳定运行

完成标志：

- 发布、回滚、Nginx、任务、告警、通知、导出、备份至少完成一轮主链路回归
- 已识别并处理主要兼容问题

### M3：迁移演练与回滚演练完成

里程碑目标：

- 完成从 SQLite 到 PostgreSQL 的演练迁移
- 完成从 PostgreSQL 回退到 SQLite 的演练

完成标志：

- 有迁移检查记录
- 有回滚演练记录
- 数据一致性和可用性结论明确

### M4：PostgreSQL 成为主阶段标准

里程碑目标：

- PostgreSQL 成为文档、部署、验收和版本建议中的主数据库

完成标志：

- 新环境默认推荐 PostgreSQL
- 正式验收口径以 PostgreSQL 为主
- SQLite 退为便捷开发和轻量演示方案

---

## 11. 结论

AegisOps 进入 PostgreSQL 主阶段，并不意味着否定 SQLite 在一期的价值。SQLite 仍然适合本地快速启动、轻量演示和低成本验证；但从当前仓库的能力规模、数据复杂度和后续演进方向看，PostgreSQL 已经更适合作为主联调、主部署和主验收数据库。

本阶段真正要完成的，不是“支持 PostgreSQL”，而是以下三件事：

- 让 PostgreSQL 成为团队的标准联调与验收路径
- 让数据迁移、部署、备份和回滚具备明确方法
- 让后续二期能力都默认在 PostgreSQL 语境下被验证和交付

如果按本方案分阶段推进，AegisOps 可以在保留 SQLite 低门槛优势的同时，逐步把数据库底座升级到更接近真实长期运行场景的形态，为后续版本持续演进建立更稳的基础。
