## 1. 文档目的

本文档用于作为 AegisOps 每次“正式发布版本”前的统一验收口径。

它回答的不是“代码是不是已经写了很多”，而是以下更关键的问题：

1. 当前版本是否真的达到可发布状态
2. 哪些问题属于正式 Release 的阻塞项
3. 哪些能力必须形成最小闭环
4. 版本号、Tag、发布说明应该如何收口

本文档适用于：

- 正式生产版本发布
- 公开展示版本发布
- 面试项目的稳定演示版本发布
- 个人长期自用版本的阶段性封版

---

## 2. 发布分级建议

为了避免“只要能跑就打正式版”，建议先把发布分成三类：

### 2.1 开发版

适用于：

- 功能开发中
- 工作区未清理
- 允许存在未完成模块
- 允许前端或后端局部不稳定

特征：

- 可以提交代码
- 可以内部预览
- 不应打正式 Release Tag

### 2.2 候选版 RC

适用于：

- 主要功能已经闭环
- 构建和测试基本通过
- 只剩少量体验或文档问题

特征：

- 可打 `rc` 类型 Tag
- 可做完整演示和回归
- 仍不建议直接定义为正式生产版

### 2.3 正式 Release

适用于：

- 版本基线清晰
- 功能闭环明确
- 构建、测试、启动、冒烟全部通过
- 没有已知高风险阻塞项

特征：

- 可以打正式语义化版本 Tag
- 可以写发布说明
- 可以作为稳定演示版本、交付版本或长期使用版本

---

## 3. 使用方式

建议把清单分成三层：

- `P0 必须通过`
- `P1 建议通过`
- `P2 可延期`

判定原则：

- 只要有任意一个 `P0` 未通过，本次不得定义为正式 Release
- `P1` 未通过时，原则上不建议发正式版，除非明确降级为 RC
- `P2` 可根据节奏延后，但应在发布说明中注明已知限制

## 8. 正式 Release 执行流程模板

建议每次正式发版按以下顺序操作：

1. 冻结本次发布范围
2. 清理工作区并完成所有必要提交
3. 跑后端全量测试
4. 跑前端生产构建
5. 跑最小功能闭环冒烟
6. 更新版本号
7. 更新 README / 发布说明 / 变更摘要
8. 创建 release commit
9. 打正式 Tag
10. 推送主分支和 Tag
11. 发布后再次做冒烟检查

建议命令模板：

```powershell
git status --short
$env:GOCACHE = "$PWD\.gocache"
go test ./...
Set-Location frontend
npm run build
Set-Location ..
git tag -a vX.Y.Z -m "release: vX.Y.Z"
git push origin main
git push origin vX.Y.Z
```

## 10. 当前项目达到正式 Release 的最低门槛建议

结合 AegisOps 当前阶段，建议正式 Release 的最低门槛至少是：

- [ ] `go test ./...` 全绿

- [ ] 工作区清理干净
- [ ] 本次版本范围明确

- [ ] 当前版本号与 Tag 一致
- [ ] 至少保留上一个稳定版本可回滚

如果上述任一项未通过，建议将当前状态定义为：

- 开发版
- 候选版 RC
- 阶段演示版

而不是正式 Release。

## 11. 一句话结论

正式 Release 的标准，不是“功能已经很多”，而是：

`版本基线清楚 + 构建测试通过 + 核心闭环成立 + 安全边界清晰 + 可回滚`

只要这五件事里还有明显短板，AegisOps 就更适合继续收口，而不是仓促打正式发布标签。
