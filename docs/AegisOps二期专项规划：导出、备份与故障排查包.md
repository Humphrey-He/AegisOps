# AegisOps 二期专项规划：导出、备份与故障排查包

## 1. 文档目的

本文档用于规划 AegisOps 下一期中与“数据带走能力”直接相关的一组功能：

1. 导出
2. 备份
3. 故障排查包
4. 恢复预案

这组功能的目标不是做成一个传统意义上的“报表中心”，而是让 AegisOps 在个人博客和少量自建服务场景中具备以下现实价值：

- 出故障时，可以快速带走现场
- 迁移机器时，可以带走关键配置
- 重装系统时，可以恢复运维资产
- 对外求助时，可以分享脱敏后的排障包

本文档重点回答以下问题：

1. 本期到底要导出什么，不导出什么
2. 哪些内容属于“备份导出”，哪些属于“排障导出”
3. 前端侧应该如何提供导出入口和下载体验
4. 后端侧应该如何组织导出数据、压缩包和脱敏策略
5. 这一期完成后，AegisOps 对个人自建服务场景的实用性会提升到什么程度

---

## 2. 本期定位

本期不是做成企业级归档平台，也不是做复杂 BI 报表。

本期要解决的是 AegisOps 当前最现实的三个短板：

1. 缺少系统级“带走能力”  
2. 缺少问题现场“打包能力”  
3. 缺少个人自建平台“迁移和恢复抓手”

因此，本期更准确的定位是：

- 为个人与小规模自建服务场景补齐“最小可用导出闭环”
- 为任务、审计、告警、Nginx 配置、服务发布等已有能力增加“可下载、可留档、可分享”的出口
- 为后续通知告警、健康检查、备份恢复体系打一个统一的数据出口底座

本期完成后，AegisOps 应至少具备以下体验：

1. 用户可以导出系统配置快照
2. 用户可以导出单个服务、单个 Nginx 节点、单个主机的排障包
3. 用户可以导出某次发布任务的完整现场
4. 用户可以导出某段时间内的审计、任务、告警记录
5. 用户可以下载可恢复的系统备份包
6. 用户可以在导出时选择“脱敏导出”

## 3. 本期范围

### 3.1 纳入本期

- 系统配置导出
- SQLite 数据备份导出
- 服务配置与发布记录导出
- Nginx 配置版本导出
- 主机 / Docker / Registry 资源配置导出
- 任务 / 审计 / 告警 / 健康检查导出
- 故障排查包导出
- 脱敏导出
- 备份包元数据与校验信息

### 3.2 适度扩展纳入本期

- 导出任务化
- 压缩包下载
- 简单恢复预案文档生成
- 定期备份任务的接口预留

### 3.3 暂不纳入本期

- Excel 报表中心
- 巨量日志归档系统
- 对象存储归档
- 自动增量备份调度
- 跨实例远程备份同步
- 一键恢复到完整运行态
- 二进制容器镜像导出

本期重点是“能带走关键现场和关键配置”，不是“把所有运行数据都做成报表和档案馆”。

## 4. 与现有能力的衔接

当前项目已经具备多类适合被纳入导出体系的数据源：

- 任务中心：任务、步骤、日志
- 审计日志
- 告警事件与通知记录
- 主机、Docker、Registry、Service、Nginx 资源模型
- 服务发布记录与健康检查记录
- Nginx 配置版本与远端备份逻辑

这意味着本期不需要重新发明一套存储模型，而是要做两件事：

1. 建立统一导出视图
2. 建立统一打包和脱敏规则

建议复用原则如下：

1. 导出优先从数据库中的结构化数据读取
2. 运行日志优先从任务日志和已有记录中抽取
3. Nginx 配置导出优先基于已存储的配置版本，而不是临时在线抓远端文件
4. 故障排查包应优先围绕任务、发布、告警事件来组织

## 5. 本期能力分层

建议本期把导出能力拆成四层：

### 5.1 资源配置导出

用于迁移、留档和人工检查。

包括：

- 主机配置
- Docker 节点配置
- Registry 配置
- Service 定义
- Nginx 节点配置
- Nginx 配置版本
- 告警规则
- 通知通道

### 5.2 运行记录导出

用于审计、回顾和问题复盘。

包括：

- 任务列表与任务详情
- 任务步骤与任务日志
- 审计日志
- 告警事件
- 通知发送记录
- 健康检查记录
- 主机可用性检查记录

### 5.3 故障排查包

用于“一次事故 / 一次失败发布 / 一次 reload 失败”的现场打包。

包括：

- 任务基本信息
- 任务步骤
- 任务日志
- 关联审计记录
- 关联告警事件
- 关联通知记录
- 关联资源快照
- 关联服务版本 / Nginx 配置版本
- 生成时间和系统版本信息

### 5.4 系统备份包

用于重装、迁移和最小恢复。

包括：

- SQLite 数据库文件
- 配置快照
- 导出清单 manifest
- 数据校验摘要
- 恢复说明

## 6. 前端侧开发规划

## 6.1 前端目标

前端本期目标不是“多一个导出按钮”，而是建立三类用户心智统一的导出入口：

1. 配置导出
2. 记录导出
3. 排障打包

前端需要让用户清楚知道：

- 导出的是什么
- 是否经过脱敏
- 导出的范围是什么
- 导出结果能拿来做什么

## 6.2 前端页面范围

建议新增或增强以下页面和入口：

### A. 系统备份页

建议路径：

- `/settings/backups`

页面内容建议包括：

- 立即创建备份
- 下载最近备份
- 备份历史列表
- 备份大小
- 创建时间
- 是否脱敏
- 校验摘要
- 恢复说明入口

### B. 导出中心页

建议路径：

- `/settings/exports`

页面内容建议包括：

- 资源配置导出
- 运行记录导出
- 故障排查包导出
- 导出历史
- 导出状态

首期不需要做得很复杂，但建议统一入口，不要散落在各个页面完全找不到。

### C. 服务详情页导出增强

建议增加以下操作：

- 导出服务定义 JSON
- 导出发布历史
- 导出最近一次发布排障包
- 导出健康检查记录

### D. Nginx 页导出增强

建议增加：

- 导出当前节点配置
- 导出配置版本历史
- 导出某次 publish / reload 失败排障包

### E. 主机详情页导出增强

建议增加：

- 导出主机配置
- 导出最近可用性检查记录
- 导出离线事件排障包

### F. 任务详情页导出增强

建议增加：

- 导出任务 JSON
- 导出任务日志文本
- 导出完整排障包 ZIP

### G. 审计页 / 告警页导出增强

建议增加：

- 按筛选条件导出 CSV
- 按时间范围导出 JSON

---

## 6.3 前端交互设计重点

### 6.3.1 不同导出类型必须区分清楚

导出入口至少要明确区分：

- 导出配置
- 导出记录
- 导出排障包
- 导出系统备份

不要只做一个笼统的“导出”按钮，否则用户无法判断结果是否可用于恢复、排障还是审计。

### 6.3.2 导出前提供范围选择

建议用户在导出前可选择：

- 时间范围
- 资源范围
- 是否包含关联记录
- 是否脱敏
- 导出格式

### 6.3.3 导出状态应可追踪

本期建议把较重的导出也纳入任务中心：

- 导出中
- 打包成功
- 打包失败
- 可下载

### 6.3.4 强调脱敏导出

前端必须明确展示：

- 默认脱敏导出
- 包含敏感配置时的风险提示
- 哪些字段会被遮盖

## 7. 后端侧开发规划

## 7.1 后端目标

后端本期不是单纯拼几个下载接口，而是建立一套稳定的“数据出站能力”。

后端目标包括：

1. 统一组织导出数据
2. 支持脱敏策略
3. 支持压缩打包
4. 支持任务化导出
5. 为未来恢复能力预留标准输入

## 7.2 后端模块拆分建议

建议新增或增强以下模块：

### A. export 模块

职责：

- 接收导出请求
- 按导出类型组织数据
- 生成 JSON / CSV / TXT / ZIP
- 返回文件下载信息
- 记录导出任务和状态

建议目录：

- `internal/export`

### B. backup 模块

职责：

- 生成系统备份包
- 打包 SQLite 数据库
- 打包配置快照
- 生成恢复说明
- 输出 manifest 和 checksum

建议目录：

- `internal/backup`

### C. redact / sanitize 模块

职责：

- 统一做脱敏处理
- 控制 Secret、Token、Webhook、邮箱密码等敏感字段输出
- 为导出、告警、分享场景复用

建议目录：

- `internal/redact`

### D. incident bundle 组织器

职责：

- 基于任务 ID / release ID / nginx 操作 / host 离线事件
- 聚合任务、审计、告警、通知和资源快照
- 生成一键排障包

建议可作为 `internal/export` 的子模块实现。

## 7.4 后端导出类型设计

## 7.4.1 资源配置导出

目标：

- 把“配置是什么”带走

建议支持：

- 单个主机
- 单个 Docker 节点
- 单个 Registry
- 单个服务定义
- 单个 Nginx 节点
- 单个 Nginx 配置版本
- 告警规则
- 通知通道

建议输出结构：

- `resource.json`
- `related-resources.json`
- `manifest.json`

## 7.4.2 运行记录导出

目标：

- 把“最近发生了什么”带走

建议支持：

- 审计日志按时间范围导出
- 任务记录按时间范围导出
- 告警记录按时间范围导出
- 健康检查记录按服务或时间范围导出

建议格式：

- `CSV` 用于表格和人工查看
- `JSON` 用于二次处理

## 7.4.3 故障排查包

目标：

- 围绕单次问题场景一键打包

建议首期支持四类入口：

1. 按 `taskId` 导出
2. 按 `releaseId` 导出
3. 按 `nginx node + taskId` 导出
4. 按 `host offline eventId` 导出

压缩包建议包含：

- `manifest.json`
- `summary.md`
- `task.json`
- `task-steps.json`
- `task-logs.txt`
- `audits.json`
- `alerts.json`
- `notification-records.json`
- `health-checks.json`
- `resource-snapshot.json`

## 7.4.4 系统备份包

目标：

- 把“可恢复的最小系统状态”带走

建议包含：

- SQLite 数据库文件
- 当前配置快照
- 后端版本信息
- schema 版本信息
- 恢复步骤说明

注意：

- 本期做“可下载备份包”
- 不要求本期做“全自动恢复到运行态”

## 7.5 脱敏策略设计

本期必须默认支持脱敏导出。

### 默认应脱敏的字段

- Secret 明文
- SSH 密钥内容
- Docker TLS 原始证书
- Registry Basic Token
- 企业微信 webhook
- Telegram bot token
- 邮箱密码 / SMTP 凭证
- Session token
- JWT

### 可保留的字段

- Secret 名称
- Secret 类型
- 脱敏后的占位值
- 被哪些资源使用
- 更新时间

### 建议策略

- 前端默认勾选“脱敏导出”
- 非脱敏导出需要更高权限和二次确认
- 故障排查包默认必须脱敏

## 7.7 任务化建议

本期建议以下导出走任务中心：

- 故障排查包
- 系统备份包
- 时间范围较大的审计/任务/告警导出

优点：

- 避免大导出阻塞请求
- 用户可在任务中心看到打包进度
- 导出失败时可留日志和错误原因

建议任务类型：

- `export.resource`
- `export.records`
- `export.incident_bundle`
- `backup.system`

## 7.8 与恢复能力的关系

本期虽然不要求做完整恢复系统，但导出和备份设计必须天然兼容未来恢复。

因此建议：

1. manifest 中带版本号
2. 备份包里带 schema 信息
3. 资源导出 JSON 尽量靠近内部 DTO，但不要暴露原始敏感字段
4. 未来如做导入接口，优先复用本期导出结构

建议按以下顺序推进：

- 服务定义导出
- Nginx 配置版本导出

- 按任务导出
- 聚合任务、审计、告警、通知、健康检查

### 阶段四：系统备份包

- SQLite 备份
- 配置快照
- manifest 与恢复说明

### 阶段五：前端导出中心

- 导出中心页
- 备份页
- 服务 / Nginx / 任务详情直达导出入口

### 阶段六：记录导出完善

- 审计 CSV
- 告警 CSV
- 时间范围导出

## 9. 本期验收标准

建议以以下闭环作为总验收：

### 场景一：失败发布排障

1. 某次服务发布失败
2. 用户进入任务详情
3. 点击导出排障包
4. 下载 ZIP
5. ZIP 中包含任务、日志、审计、告警、健康检查和资源快照

### 场景二：Nginx 配置留档

1. 用户进入 Nginx 配置页
2. 导出某个配置版本
3. 下载内容可清晰看到版本、内容、状态、创建人、时间

### 场景三：系统迁移准备

1. 用户创建系统备份
2. 下载备份包
3. 备份包中含数据库、manifest、恢复说明
4. 敏感信息按策略脱敏或受控输出

### 场景四：审计带走

1. 用户选择时间范围
2. 导出审计 CSV 或 JSON
3. 下载结果可用于人工复盘

---

## 10. 风险点与注意事项

### 10.1 不要把导出功能只做成前端拼接下载

尤其是故障排查包和系统备份，必须由后端统一打包，否则数据不完整且无法做脱敏和校验。

### 10.2 不要让导出直接暴露敏感字段

默认必须脱敏，尤其是 Secret、Webhook、密码、TLS 证书等。

### 10.3 不要把“备份”误当成“恢复”

本期做的是备份包和恢复预案，不是完整一键恢复系统。

### 10.4 大导出不要走同步请求

应尽量任务化，否则前端体验差，也容易压住 SQLite 写链路。

### 10.5 排障包不要做成无结构文本

必须包含结构化 JSON 和简要说明，否则后续二次处理和对外协作价值很低。

## 11. 一句话结论

这一期的本质，不是“补一个下载按钮”，而是把 AegisOps 从“能看、能操作”的控制台，推进到“出事能带走现场、迁移能带走配置、重装能带走底稿”的个人运维平台。
