# AegisOps 二期专项规划：权限细粒度、密钥管理与任务调度

## 1. 文档目的

本文档用于规划 AegisOps 下一阶段中与“平台控制力、安全边界、执行可靠性”直接相关的三组能力：

1. 权限细粒度
2. 密钥管理
3. 任务调度

这三组能力决定 AegisOps 能否从“一个可登录、可操作资源的运维后台”，进一步提升为“一个可控、可审计、可扩展、可长期自用的轻量运维控制面”。

本文档重点回答以下问题：

1. 当前这三块分别做到什么程度
2. 当前缺口会带来哪些真实风险
3. 二期应该补什么，不应该一口气做什么
4. 前端和后端各自需要承担哪些改造工作
5. 二期完成后，AegisOps 会在哪些方面真正变得更像“可持续使用的平台”

---

## 2. 本期定位

本期不是简单补几个页面，也不是继续横向铺新模块。

本期的本质，是把 AegisOps 的三个底座从“能用”推进到“可控”：

1. 权限从“接口级 RBAC”推进到“高风险操作可收口、资源范围可限制”
2. 密钥从“有 Secret 表”推进到“敏感配置统一托管、统一脱敏、统一审计”
3. 任务从“执行记录模型”推进到“真正可调度、可重试、可取消、可扩展的执行体系”

本期完成后，AegisOps 至少应具备以下平台特征：

1. 普通用户即使能看到某类资源，也不一定能操作所有资源
2. 通知、主机、Docker、Registry、Nginx 等敏感配置不再散落明文
3. 长耗时和高风险动作不再依赖同步请求直接跑完，而是进入统一调度链路
4. 调度失败、超时、重试、取消、并发冲突能够被明确识别和追踪
5. 权限、密钥、任务三条线能与审计日志形成统一闭环

---

## 3. 当前现状与主要缺口

## 3.1 权限细粒度现状

当前项目已经具备基础 RBAC 骨架：

- 有用户、角色、权限三层模型
- 有权限码，如 `services.view`、`services.manage`、`services.release`
- 大部分业务路由已经接入后端权限中间件
- 管理员初始化、权限补种、角色权限绑定已经可以工作

当前最主要的缺口是：

1. 当前权限主要是“接口级”和“功能级”，还不是“资源范围级”
2. 同一类资源的“看全部 / 看本组 / 看自己负责的 / 只看白名单资源”尚未建模
3. `IsAdmin` 仍然是全量绕过，适合一期，不适合长期扩展
4. 有些高风险动作没有独立到足够细的权限点
5. 个别写接口的权限要求偏松，例如任务相关写接口仍可能只挂了 `tasks.view`
6. 前端菜单隐藏和按钮禁用不是授权本身，后端目前也还没有“数据范围过滤”这层

这些缺口带来的直接风险是：

- 用户权限会停留在“能不能进页面”，而不是“能不能动这台机器”
- 后续主机、服务、Nginx、导出、备份等能力越多，越容易出现权限绕过或权限过宽
- 当平台从“自己一个人用”扩展到“自己 + 合作者”时，权限模型很快失去控制力

## 3.2 密钥管理现状

当前项目已经有可用的 Secret 能力：

- Secret 具备单独模型
- 敏感值通过应用层 AES-GCM 加密存储
- 返回给前端时使用脱敏值
- Host / Docker / Registry / Nginx / Terminal 已经能复用这套 Secret 服务

当前最主要的缺口是：

1. 敏感配置并没有全部收口到 Secret 中心
2. 通知渠道配置虽然字段名叫 `ConfigEncrypted`，但当前实际仍是明文存储、明文返回
3. Secret 缺少“被谁引用、能否删除、删除后影响什么”的引用管理
4. Secret 缺少“何时被读取、由哪个模块读取、是否异常读取”的使用审计
5. Secret 缺少轮换、版本、禁用、到期策略
6. 导出、备份、排障包等二期能力如果直接复用当前实现，容易把敏感配置带出

这些缺口带来的直接风险是：

- 有 `notifications.view` 的用户可能看到 webhook、bot token、SMTP 密码
- 删除某个 Secret 后，相关主机或节点配置会变成悬空引用
- 平台无法回答“某个密钥实际被哪些资源依赖”
- 未来做备份、导出、分享时，敏感信息泄露风险明显偏高

## 3.3 任务调度现状

当前项目已经有比较完整的任务中心基础：

- 有 `tasks / task_steps / task_logs`
- 服务发布、主机测试、Docker 操作、Nginx 操作等已能任务化记录
- 状态、步骤、日志、任务详情链路已经有雏形

当前最主要的缺口是：

1. 当前更像“任务执行记录中心”，还不是“真正的调度系统”
2. 大多数任务仍是请求链路里直接执行，任务表更多承担记录功能
3. 没有独立 worker、任务分发器、调度器、重试器
4. 没有真正的定时任务体系，例如主机巡检、定时备份、定时探活
5. 没有超时回收、取消中断、失败重试、退避策略、并发限制等关键能力
6. 当前锁更多是进程内锁，单实例可用，多实例不够稳妥

这些缺口带来的直接风险是：

- 高耗时任务会拉长接口请求时间，前端体验和稳定性都受影响
- 一旦动作失败，平台只能“记失败”，但不擅长“调度重跑”
- 做主机巡检、定时备份、导出打包、通知补发时，会越来越依赖临时拼逻辑
- 将来如果不是单进程单实例部署，任务并发冲突会明显增多

## 4. 本期总体目标

本期建议聚焦以下三个总目标：

### 4.1 最小权限原则真正落地

目标不是继续增加更多权限码，而是让权限开始真正决定：

- 谁能看到资源
- 谁能修改资源
- 谁能执行高风险动作
- 谁能查看敏感信息
- 谁能触发导出、备份、非脱敏操作

### 4.2 敏感配置统一纳入 Secret 中心

目标不是把所有配置都复杂化，而是把真正敏感的信息统一接到 Secret：

- SSH 密码 / SSH 私钥
- Docker Token / TLS 材料
- Registry Basic / Token
- Telegram Bot Token
- 企业微信 Webhook
- SMTP 账号密码
- 后续其他三方平台接入凭据

### 4.3 任务中心升级为轻量调度底座

目标不是一步做成大型任务平台，而是先把最关键的调度能力补齐：

- 同步动作与异步执行解耦
- 可重试、可取消、可超时
- 支持最小定时巡检
- 支持并发控制
- 支持任务来源区分：手工触发 / 系统触发 / 定时触发

## 5. 本期范围

### 5.1 纳入本期

- 权限点重新梳理与细化
- 资源范围权限建模
- 高风险操作权限隔离
- 任务相关写接口权限收紧
- 通知渠道敏感配置 Secret 化
- Secret 引用关系管理
- Secret 读取审计
- Secret 删除前依赖检查
- 任务队列与 worker 雏形
- 任务重试、取消、超时、并发限制
- 定时任务底座
- 主机可用性巡检任务化
- 健康检查任务化
- 导出 / 备份等重操作的任务化接入能力预留

### 5.2 暂不纳入本期

- 完整多租户权限体系
- 复杂审批流
- 外部 KMS / Vault / HSM 正式接入
- 分布式消息队列中间件
- 多活 worker 集群调度
- 完整 DAG 工作流编排
- 大规模任务优先级抢占调度

本期目标是“把底座补稳”，不是“把平台一次做重”。

## 6. 设计原则

### 6.1 权限永远以后端为准

前端可以做按钮隐藏、菜单裁剪、危险提示，但不能替代授权。

### 6.2 敏感信息默认不出库

只要一个字段的真实值可能被用于登录、连接、推送、发信，它就应优先进入 Secret 中心，不应继续以普通配置字段长期存在。

### 6.3 任务记录与任务执行解耦

`Task` 不应只是“执行后写结果”，而应成为调度系统中的正式运行记录。

### 6.4 高风险动作必须可追踪

发布、回滚、Nginx 生效、非脱敏导出、密钥变更、通知测试等高风险动作必须同时具备：

- 权限校验
- 审计记录
- 任务状态
- 错误可追踪

### 6.5 优先支持当前真实使用场景

优先支持单机部署、SQLite、少量资源、自己或小范围协作使用，不以“理论最强架构”为第一优先级。

## 7. 权限细粒度专项规划

## 7.1 权限目标

本期要把权限从“有没有这个页面的访问权”，推进到“有没有操作这类资源的哪一部分”的级别。

建议最终形成三层控制：

1. 功能权限
2. 资源范围权限
3. 高风险动作权限

## 7.2 当前权限模型要补的重点

建议保留当前 `users / roles / permissions / user_roles / role_permissions` 主结构，在此基础上补“范围”和“动作”的表达能力。

建议新增或细化权限点：

- `tasks.view`
- `tasks.create`
- `tasks.cancel`
- `tasks.retry`
- `tasks.dispatch`
- `terminal.open`
- `terminal.manage`
- `exports.unmasked`
- `backups.download.unmasked`
- `secrets.use`
- `secrets.rotate`
- `notifications.secret.view`
- `notifications.secret.manage`
- `services.rollback`
- `nginx.reload`
- `nginx.publish`
- `hosts.test`
- `hosts.operate`

说明：

- 当前很多 `manage` 权限过于宽泛，二期应把“编辑配置”和“执行动作”分开
- “看资源”和“调任务”也应分开
- “能看通知配置”与“能看通知敏感参数”必须分开

## 7.3 资源范围权限设计建议

建议在现有 RBAC 之上，新增“角色权限范围绑定”模型。

建议新增表：

### 7.3.1 `role_permission_scopes`

建议字段：

- `id`
- `role_id`
- `permission_id`
- `resource_type`
- `scope_type`：`ALL` / `GROUP` / `OWNER` / `RESOURCE_SET`
- `scope_value_json`
- `created_at`
- `updated_at`

建议首期支持的范围类型：

- `ALL`：全量资源
- `GROUP`：主机组、服务组、Nginx 节点组
- `OWNER`：只看自己创建或自己负责的资源
- `RESOURCE_SET`：显式绑定少量资源 ID

建议首期优先纳入范围控制的资源：

- Host
- DockerNode
- Registry
- Service
- NginxNode
- ExportJob
- BackupRecord

## 7.4 后端改造建议

后端需要完成以下改造：

1. 在权限判断后追加资源范围过滤
2. 列表接口支持按当前用户的可见范围自动收口
3. 单资源详情接口在查询后再校验一次资源可见性
4. 动作接口在执行前校验“对该资源是否有操作权”
5. 高风险接口支持更细粒度权限码

建议新增能力模块：

- `internal/rbac/scope.go`
- `internal/rbac/policy.go`

建议优先落地的接口：

- `GET /api/hosts`
- `GET /api/services`
- `GET /api/nginx/nodes`
- `GET /api/registries`
- `POST /api/services/:id/releases`
- `POST /api/nginx/nodes/:id/reload`
- `POST /api/hosts/:id/test-ssh`
- `GET /api/exports/:id/download`

## 7.5 前端改造建议

前端不只要“隐藏菜单”，还要体现权限的边界感。

建议补以下能力：

- 角色页支持配置权限范围
- 列表页支持明确显示“当前仅显示你有权限的资源”
- 无操作权限时展示原因，不只是按钮灰掉
- 高风险按钮展示更明确的确认语义
- 当用户有 `view` 无 `operate` 时，详情可见但动作区只读

建议优先改造页面：

- 用户管理页
- 角色权限页
- 主机列表 / 主机详情
- 服务列表 / 服务详情
- Nginx 节点页
- 导出 / 备份相关页面

## 7.6 权限专项验收标准

1. 普通用户能登录，但只能看到被授权范围内的主机、服务、Nginx 节点
2. 用户即使知道其他资源 ID，也不能越权访问详情或执行动作
3. `tasks.view` 不再默认拥有任务写权限
4. 非脱敏导出必须有专门权限
5. 通知渠道敏感配置查看必须有单独权限
6. 关键写接口的 403 行为稳定可测试

## 8. 密钥管理专项规划

## 8.1 密钥管理目标

本期目标不是引入重型外部密钥系统，而是先把 AegisOps 内部的敏感信息治理做完整：

1. 敏感配置统一 Secret 化
2. 明确 Secret 被谁引用
3. 明确 Secret 被谁读取
4. 默认脱敏、默认不回显
5. 删除和轮换可控

## 8.2 本期要优先收口的敏感配置

建议优先纳入 Secret 中心的对象：

- Telegram Bot Token
- Telegram Webhook URL
- 企业微信 Webhook
- SMTP 用户名 / 密码
- SMTP 发件认证配置
- 后续第三方平台凭据

当前建议的方向不是让 `notification_channels` 自己存所有敏感配置，而是：

- 普通字段继续放在通知渠道表
- 敏感字段改为引用 `secret_id`

例如通知渠道建议拆成：

- `name`
- `type`
- `enabled`
- `language`
- `default_target`
- `public_config_json`
- `config_secret_id`

## 8.3 数据模型建议

建议在现有 `secrets` 基础上新增以下能力。

### 8.3.1 `secret_references`

建议字段：

- `id`
- `secret_id`
- `resource_type`
- `resource_id`
- `field_name`
- `created_by`
- `created_at`

用途：

- 标记某个 Secret 被哪个资源、哪个字段引用
- 删除 Secret 前做依赖检查
- Secret 详情页展示“被哪些对象使用”

### 8.3.2 `secret_read_audits`

建议字段：

- `id`
- `secret_id`
- `resource_type`
- `resource_id`
- `action`
- `operator_id`
- `task_id`
- `result`
- `error_message`
- `created_at`

用途：

- 记录何时发生过解密使用
- 支持排查异常读取
- 与任务中心、审计日志关联

### 8.3.3 可选：增强 `secrets`

可增补字段：

- `purpose`
- `status`
- `key_version`
- `last_rotated_at`
- `expires_at`

本期可以先做最小版，不一定一次把轮换体系全部做满。

## 8.4 后端改造建议

后端需要完成以下改造：

1. Secret 创建后支持建立引用关系
2. 资源更新 Secret 绑定时，同步更新引用记录
3. Secret 删除前检查引用
4. 真正发生解密时写读取审计
5. 通知渠道配置改为“敏感信息走 Secret，普通信息走普通表”
6. 导出、备份、故障排查包默认只导出脱敏值和 Secret 引用，不导出明文

建议优先改造的模块：

- `internal/notification`
- `internal/secret`
- `internal/host`
- `internal/docker`
- `internal/registry`
- `internal/nginx`
- `internal/exporter`

## 8.5 前端改造建议

前端需要把“密钥”从普通表单字段里抽离出来。

建议交互变化：

1. 通知渠道页创建 Telegram / 邮箱通道时，不再直接保存明文 token / password
2. 表单改为“选择已有 Secret”或“新建并绑定 Secret”
3. Secret 详情页展示引用对象列表
4. 删除 Secret 时展示依赖阻塞信息
5. 高敏感字段默认只展示“已绑定 / 未绑定”，不展示真实值

建议优先改造页面：

- Secret 列表页
- Secret 详情页
- Notifications 配置页
- Registry / Docker / Host / Nginx 编辑页

## 8.6 密钥管理专项验收标准

1. 通知渠道敏感配置不再明文存储和明文返回
2. Secret 可查看引用关系
3. 被引用的 Secret 不能被直接删除，除非先解除绑定
4. 解密使用过程可追踪
5. 导出、备份、故障排查包默认不泄露明文敏感值
6. 前端所有敏感输入至少有一条“绑定 Secret”链路

## 9. 任务调度专项规划

## 9.1 任务调度目标

本期要把当前“任务记录中心”推进为“轻量调度底座”。

建议先达成以下最小能力：

1. 手工触发动作异步化
2. 系统触发动作任务化
3. 定时任务可运行
4. 失败任务可重试
5. 运行任务可取消
6. 长时间卡住的任务可超时回收
7. 同一资源高风险动作可并发限制

## 9.2 任务体系建议分层

建议二期把任务体系分成三层：

### A. 任务定义层

说明“是什么任务、来自哪里、默认策略是什么”。

### B. 调度分发层

负责把任务放入待执行队列、判断是否可执行、由 worker 领取。

### C. 运行记录层

负责记录任务状态、步骤、日志、结果、错误原因。

当前项目已经比较接近 C 层，二期要重点补 A 层和 B 层。

## 9.3 数据模型建议

建议保留现有 `tasks / task_steps / task_logs`，并新增以下模型。

### 9.3.1 `scheduled_jobs`

建议字段：

- `id`
- `name`
- `type`
- `enabled`
- `cron_expr`
- `target_type`
- `target_id`
- `payload_json`
- `retry_policy_json`
- `timeout_seconds`
- `concurrency_key`
- `last_run_at`
- `next_run_at`
- `created_by`
- `updated_by`
- `created_at`
- `updated_at`

用途：

- 定义定时巡检、定时备份、定时健康检查等任务

### 9.3.2 `task_dispatches`

建议字段：

- `id`
- `task_id`
- `source`：`MANUAL` / `SYSTEM` / `SCHEDULED`
- `job_id`
- `status`：`PENDING` / `DISPATCHED` / `RUNNING` / `SUCCESS` / `FAILED` / `CANCELED` / `TIMEOUT`
- `retry_count`
- `max_retry`
- `timeout_seconds`
- `concurrency_key`
- `lease_owner`
- `lease_expires_at`
- `queued_at`
- `started_at`
- `finished_at`

用途：

- 让“任务记录”和“任务调度状态”分层
- 支持后续 worker、超时、重试、抢占等能力

### 9.3.3 可选：`task_cancellations`

如果不想一开始把取消状态放太重，也可以先用任务表字段表达，后续再拆。

## 9.4 后端改造建议

建议按最小可行调度器路线推进：

### 9.4.1 先做进程内 worker

本期先不强依赖 Redis 或外部队列，优先在当前服务进程中实现：

- Dispatcher
- Worker
- Timeout Watcher
- Retry Scheduler

### 9.4.2 接口改为“创建任务并返回”

对于高耗时操作，建议统一为：

1. API 请求只负责创建任务和调度记录
2. 后台 worker 真正执行
3. 前端通过任务详情页查看进度和结果

优先改造的动作：

- 主机 SSH 测试
- Docker 测试和容器动作
- Registry 测试
- Nginx test / reload / publish / rollback
- 服务发布 / 升级 / 回滚
- 导出 / 备份

### 9.4.3 补最小调度能力

建议首期必须补齐：

- 重试次数
- 固定退避或指数退避
- 超时终止
- 取消标记
- 并发键冲突拒绝或排队

### 9.4.4 补定时任务底座

建议首期就做最少两个真实定时场景：

1. 主机可用性巡检
2. 服务健康检查巡检

可选第三个场景：

3. 定时备份

## 9.5 前端改造建议

前端应把任务页从“查看日志”升级为“控制执行”。

建议新增或增强：

- 任务来源标签：手工 / 系统 / 定时
- 调度状态字段
- 重试按钮
- 取消按钮
- 超时标记
- 并发冲突提示
- 定时任务列表页
- 定时任务创建 / 编辑页

建议优先改造页面：

- 任务列表页
- 任务详情页
- Dashboard 最近任务区
- 主机详情页可用性区块
- 服务详情页健康检查区块
- 系统设置中的调度任务页

## 9.6 调度专项验收标准

1. 高耗时操作不再长时间阻塞接口请求
2. 任务可区分手工触发、系统触发、定时触发
3. 任务失败后可按策略重试
4. 长时间未完成任务会进入超时状态
5. 用户可取消尚未完成的任务
6. 主机巡检和服务巡检可按计划自动运行
7. 同一资源的关键动作并发时能被识别和限制

## 10. 前后端分工建议

## 10.1 前端侧重点

前端二期重点不是做更多页面数量，而是做更清晰的控制面体验：

1. 角色权限和资源范围配置可视化
2. Secret 绑定和依赖关系可视化
3. 任务调度和执行状态可视化
4. 高风险动作确认语义更明确
5. 权限不足、范围受限、任务冲突这些状态要能被用户看懂

## 10.2 后端侧重点

后端二期重点不是再加几个 CRUD，而是把底层约束补齐：

1. 授权判断从“有没有权限码”升级到“有没有这个资源的权限”
2. 敏感配置从“分散加字段”升级到“统一 Secret 引用”
3. 任务执行从“请求里直接跑”升级到“调度后异步执行”
4. 任务状态、权限状态、密钥状态与审计日志打通

## 12. 本期测试建议

建议二期至少覆盖以下测试：

1. 普通用户越权访问其他资源详情时返回 403
2. 范围内用户能查到资源，范围外用户查不到
3. 通知渠道敏感配置不再明文存储 / 明文返回
4. Secret 被引用时删除失败并返回依赖信息
5. Secret 真实解密使用会留下审计或读取记录
6. 发布、Nginx、导出等高耗时动作创建任务后异步执行成功
7. 任务超时、取消、重试链路可以稳定复现
8. 定时主机巡检和定时服务巡检可自动创建任务并落日志

## 13. 风险与注意事项

### 13.1 不要把权限细化只做成“更多字符串权限码”

如果没有资源范围控制，权限再多也仍然只是功能开关，不是实际授权体系。

### 13.2 不要把通知敏感配置继续当普通 JSON 字段保存

这是当前最容易形成真实泄露风险的一处缺口，优先级应非常高。

### 13.3 不要把任务调度理解成“多一张任务表”

如果没有 dispatcher、worker、重试、超时，任务中心就还是记录系统，不是调度系统。

### 13.4 不要过早把调度做得过重

二期先做进程内轻量 worker 和最小定时能力即可，先解决真实问题，再决定是否引入 Redis / Asynq / 外部调度器。

### 13.5 不要忽略审计联动

权限收紧、密钥读取、任务取消、任务重试、非脱敏导出，这些都应该进入审计链路。

---

## 14. 一句话结论

这一期的重点，不是继续横向堆页面，而是把 AegisOps 的三条底座补到真正可长期使用的程度：

- 权限开始真正约束“谁能动哪台资源”
- 密钥开始真正统一管理“哪些敏感信息不能裸奔”
- 任务开始真正承担“哪些动作应该被调度、被重试、被追踪”

只有把这三块补稳，AegisOps 才会从“一个功能已经很多的个人运维后台”，真正迈向“一个可控、可信、可持续扩展的轻量运维平台”。
