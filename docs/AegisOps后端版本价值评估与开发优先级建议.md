# AegisOps 后端版本价值评估与开发优先级建议

## 1. 文档目的

本文档用于从后端视角评估 AegisOps 从 `v1.0.0` 走向 `v2.0.0` 的版本价值，并给出可执行的开发优先级建议。

重点回答三个问题：

1. 后端继续演进的核心价值是什么。
2. 哪些能力应该优先开发，哪些能力应该后置。
3. 每个阶段应交付什么，如何验收。

本文档不替代已有版本规划，而是作为后端侧的落地优先级说明。

---

## 2. 当前后端基线评价

当前 AegisOps 后端已经具备一套轻量运维控制台的基础能力，不再是简单脚手架。

已具备的核心模块包括：

- 身份认证与管理员初始化
- 用户、角色、权限、RBAC
- 审计日志
- 主机管理与 SSH 测试
- Secret 管理与敏感配置脱敏
- Docker 节点管理
- Registry 管理
- 服务定义、发布、升级、回滚
- Nginx 节点与配置管理
- 任务中心、任务步骤、任务日志
- WebSSH / 终端能力
- 通知通道、告警规则、告警事件
- 健康检查
- 导出、备份、故障排查包基础能力
- SQLite / PostgreSQL 切换能力

这说明 `v1.0.0` 的价值已经从“功能原型”进入“可联调、可演示、可继续打磨”的阶段。

但当前后端仍有几个明显边界：

- 很多能力已经存在，但闭环还不够强。
- 部分长耗时动作仍偏同步或半任务化。
- 告警、通知、任务、审计之间还需要进一步统一语义。
- Secret 与权限具备基础能力，但还没有完全进入企业级治理状态。
- PostgreSQL 已接入，但长期生产稳定性还需要更多真实链路验证。

---

## 3. 后端版本价值判断

从 `v1.0.0` 到 `v2.0.0`，后端的核心价值不是继续增加更多模块名称，而是把已有模块串成真正的运维闭环。

目标应从：

```text
能管理资源、能触发动作
```

升级为：

```text
动作有任务、失败有告警、风险有权限、现场可导出、长期可调度
```

后端价值可以分成五层。

## 3.1 稳定性闭环价值

这是最高优先级价值。

服务发布、Nginx 生效、主机巡检、Docker 操作这类运维动作，本身不是最终价值。真正的价值在于：

- 动作失败能被发现
- 失败能生成告警
- 告警能触达用户
- 用户能回看任务与日志
- 系统能给出回滚或处理建议
- 整个过程有审计记录

如果这条链路完整，AegisOps 才像一个运维控制面，而不是普通管理后台。

## 3.2 任务执行层价值

任务执行层是后端架构升级的核心。

当前任务中心已经有任务、步骤和日志，但还需要进一步补齐：

- worker
- 队列
- 超时
- 重试
- 取消
- 并发 key
- 运行中恢复

这些能力决定后续发布、回滚、导出、备份、巡检、批量操作是否能稳定扩展。

## 3.3 安全边界价值

Secret 与权限治理决定 AegisOps 从个人工具走向小团队工具的上限。

需要重点增强：

- 高风险操作权限拆分
- 非脱敏导出权限
- Secret 引用关系
- Secret 删除保护
- Secret 读取审计
- Secret 禁用、轮换、过期状态
- 通知通道敏感配置 Secret 化

功能越多，风险面越大。安全边界必须跟着能力增长同步收紧。

## 3.4 数据带走价值

导出、备份、故障排查包的价值不是“下载文件”，而是让平台具备带走现场的能力。

生产问题发生时，用户需要拿到：

- 任务详情
- 步骤状态
- 任务日志
- 关联审计
- 关联告警
- 通知记录
- 资源快照
- 脱敏后的配置现场

这会显著提升 AegisOps 的真实排障价值。

## 3.5 协作与环境价值

环境、批量、协作、高风险保护都很有价值，但应该后置。

原因是这些能力依赖前面的任务、权限、审计和资源模型。如果基础没有稳定，提前做环境和批量操作，容易变成字段堆叠和页面堆叠。

## 4. 后端开发优先级

## 4.1 P0：稳定性与运维闭环

### 目标

让服务发布、主机离线、Nginx 失败等关键事件具备完整闭环。

### 后端交付物

- 服务发布后自动健康检查
- 健康检查失败后生成告警事件
- 告警事件关联 `task / release / resource`
- 通知记录关联 `alert event`
- 回滚建议接口稳定化
- Nginx reload / publish 失败进入统一事件
- Host offline / recovered 进入统一事件
- 高风险动作统一写审计

### 关键事件类型

```text
service_release_failed
service_health_check_failed
nginx_reload_failed
nginx_publish_failed
host_offline
host_recovered
```

### 验收标准

- 服务发布探活失败后，可以看到任务、告警、通知、回滚建议。
- Nginx reload 失败后，可以生成统一告警事件。
- 主机离线后，可以生成告警并触发通知。
- 告警事件可以反查关联任务、资源和通知记录。

---

## 4.2 P1：任务执行底座

### 目标

让所有长耗时、高风险动作进入统一后台执行体系。

### 后端交付物

- 本地 worker
- 任务队列
- 任务超时
- 失败重试
- 取消任务
- 并发 key 控制
- 运行中任务恢复策略
- 任务来源区分：手工、系统、定时

### 优先任务化对象

- 服务发布
- 服务升级
- 服务回滚
- Nginx 配置发布
- Nginx reload
- 主机 SSH 测试
- Docker 节点测试
- Registry 测试
- 导出
- 备份
- 巡检

### 验收标准

- 长任务不阻塞 HTTP 请求。
- 任务可以查看步骤和日志。
- 失败任务可以重试。
- 超时任务可以被识别。
- 运行中任务可以取消。
- 同一服务不能并发发布造成状态覆盖。

---

## 4.3 P2：导出、备份与故障排查包

### 目标

让 AegisOps 具备配置、记录和故障现场的带走能力。

### 后端交付物

- 导出中心 API
- 备份包生成
- manifest
- checksum
- 恢复说明
- 故障排查包生成
- 导出任务记录
- 默认脱敏策略
- 非脱敏导出权限

### 故障排查包内容

```text
summary.md
task.json
task-logs.txt
audits.json
alerts.json
notification-records.json
health-checks.json
resource-snapshot.json
manifest.json
```

### 验收标准

- 用户可以按任务导出故障排查包。
- 默认导出不泄露 Secret 明文。
- 导出包包含 manifest 和 checksum。
- 大型导出进入任务中心，不阻塞请求。
- 非脱敏导出必须具备专门权限。

---

## 4.4 P3：Secret 与权限治理

### 目标

让高风险能力具备更清晰的权限边界和敏感信息治理能力。

### 后端交付物

- 权限点细化：
  - `view`
  - `manage`
  - `operate`
  - `release`
  - `rollback`
  - `test`
  - `export`
- 非脱敏导出权限
- Secret 引用关系
- Secret 删除前依赖检查
- Secret 读取审计
- Secret 禁用状态
- Secret 轮换状态
- Secret 到期状态
- 通知通道敏感配置 Secret 化

### 建议顺序

1. 先做 Secret 引用治理。
2. 再做 Secret 生命周期状态。
3. 再做非脱敏导出权限。
4. 最后做资源范围权限。

### 验收标准

- 被引用的 Secret 不能被直接删除。
- 用户读取 Secret 时有审计记录。
- 通知通道不返回敏感配置明文。
- 非脱敏导出需要独立权限。
- 普通用户无法执行 release / rollback / export 等高风险动作。

---

## 4.5 P4：资源范围、环境与协作

### 目标

让 AegisOps 从单人使用走向小团队、多环境使用。

### 后端交付物

- 资源环境字段
- 项目字段
- 分组标签
- 资源查询按环境过滤
- 资源范围权限：
  - `ALL`
  - `GROUP`
  - `OWNER`
  - `RESOURCE_SET`
- 主机批量测试
- Docker 节点批量巡检
- Nginx 配置批量测试
- 服务批量发布前校验
- 高风险操作二次确认语义

### 验收标准

- 资源可以按环境过滤。
- 用户只能访问自己权限范围内的资源。
- 批量操作能生成任务并展示部分成功 / 部分失败。
- 高风险操作具备明确影响范围。

## 5. 推荐版本映射

| 优先级 | 推荐版本 | 主题 | 后端价值 |
| --- | --- | --- | --- |
| P0 | v1.1.0 | 稳定性闭环 | 让失败可感知、可通知、可回看 |
| P1 | v1.4.0 前置核心 | 任务执行底座 | 支撑所有长任务和高风险动作 |
| P2 | v1.2.0 | 导出、备份、排障包 | 提升长期使用和故障处理价值 |
| P3 | v1.3.0 | Secret 与权限治理 | 收紧团队使用和敏感信息边界 |
| P4 | v1.5.0 | 环境与协作 | 支撑小团队、多环境、批量操作 |
| 收口 | v2.0.0 | 轻量生产控制面 | 完成真实环境验收和文档收口 |

说明：

虽然版本规划中 `v1.4.0` 是任务调度与后台执行，但从后端落地角度看，任务执行底座应该适当前置。否则导出、备份、发布、巡检都会继续重复实现异步逻辑。

---

## 6. 建议开发顺序

推荐按下面顺序推进：

```text
稳定性闭环
-> 任务执行底座
-> 导出 / 备份 / 排障包
-> Secret 与权限治理
-> 环境 / 批量 / 协作
-> v2.0.0 验收收口
```

具体拆分：

1. 先把服务发布失败、健康检查失败、主机离线、Nginx 失败串成统一事件。
2. 再补本地 worker，让发布、导出、备份、巡检都进入统一执行层。
3. 然后把排障包、备份包、导出记录做成真正可下载、可追溯的能力。
4. 接着收紧 Secret、权限和非脱敏导出边界。
5. 最后补环境、批量操作和团队协作能力。

## 7. 后端架构建议

## 7.1 事件模型统一

建议将告警、通知、健康检查、发布失败都统一到事件语义下。

核心字段建议：

```text
eventType
severity
status
resourceType
resourceId
taskId
releaseId
summary
detail
suggestion
dedupeKey
firstTriggeredAt
lastTriggeredAt
```

## 7.2 任务执行统一

建议所有高风险动作都进入任务执行层：

```text
handler -> service -> task executor -> worker -> step/log -> audit/event
```

不要让 handler 直接同步执行长耗时远程动作。

## 7.3 权限过滤统一

资源范围权限不要散落在每个 handler 里。

建议抽象统一能力：

```text
ScopeFilter(user, resourceType) -> query scope
```

所有列表、详情、操作接口复用同一套范围过滤。

## 7.4 Secret 使用统一

所有敏感配置读取都应走：

```text
SecretService.DecryptValueForUse(...)
```

并统一记录读取审计。

## 8. 主要风险与控制建议

## 8.1 任务执行层复杂度风险

风险：

如果一开始就做分布式 worker、复杂队列和 DAG，容易拖慢版本。

建议：

先做单机本地 worker，支持队列、重试、超时、取消即可。

## 8.2 权限范围改造风险

风险：

资源范围权限会影响所有资源查询和操作接口，改动面很大。

建议：

先做高风险操作权限拆分，再做资源范围权限。

## 8.3 通知外链风险

风险：

Telegram、企业微信、邮件里的链接必须是外部可访问 URL，不能使用 `localhost`。

建议：

保留 `notification.public_base_url` 配置，但生产部署时必须配置为真实域名。

## 8.4 PostgreSQL 真实环境风险

风险：

远程 PostgreSQL 的迁移、初始化、网络延迟会放大启动耗时。

建议：

后续将迁移、种子、服务启动拆分得更清晰，并增加启动日志。

---

## 9. 最终建议

AegisOps 后端后续不应优先追求更多模块，而应优先追求闭环质量。

最值得优先投入的不是“再接一个平台”，而是：

- 发布失败能不能自动发现
- 告警能不能触达
- 用户能不能快速定位失败原因
- 能不能安全回滚
- 能不能导出现场
- 整个过程有没有权限和审计

如果这些能力按顺序落地，AegisOps 到 `v2.0.0` 时会更像一个真正可长期使用的轻量生产控制面，而不是一个功能很多但闭环松散的运维后台。
