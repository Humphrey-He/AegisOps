# AegisOps 二期前后端开发路线

## 1. 文档目的

本文档用于明确 AegisOps 在完成一期收口之后的第二期开发范围、阶段目标、前后端分工、验收口径与推进顺序。

本文档重点解决以下问题：

1. 二期到底做什么，不做什么
2. 后端应该按什么顺序推进
3. 前端应该按什么顺序推进
4. 前后端如何协同，避免再次出现“大量页面已存在但接口契约未冻结”的联调问题

## 2. 二期定位

二期的核心目标不是继续横向铺满所有平台能力，而是补齐“服务发布闭环”。

结合一期路线与当前项目状态，二期建议聚焦以下 6 个能力域：

1. Registry 管理
2. 服务定义
3. 服务实例
4. 发布任务
5. 服务升级
6. 服务回滚

二期明确暂不作为主目标推进的内容：

- Nginx 配置管理
- Jenkins 集成
- 备份恢复
- 指标监控与告警
- Agent 架构
- 多租户与复杂资源范围权限

因此，二期不是“大而全平台建设”，而是“从资源管理平台升级为可发布、可升级、可回滚的运维控制面”。

## 3. 二期启动前置条件

二期不建议直接在当前状态下强行启动，建议先满足以下前置条件：

### 3.1 一期后端收口

至少需要先补齐：

- Dashboard 真实接口
- WebSSH 会话与终端链路
- RBAC 真正接入后端业务接口
- Secret / Host / Docker / 容器动作审计补齐
- 动作类接口与任务中心返回模型统一

### 3.2 一期前端收口

至少需要先补齐：

- Dashboard 真实首页
- 管理员初始化真实后端接入
- 角色权限真实保存
- 终端真实后端链路接通
- 关键页面 DTO 契约稳定

### 3.3 二期契约冻结

在正式开发二期前，建议先冻结以下接口契约：

- Registry DTO
- Service DTO
- Service Instance DTO
- Release Task DTO
- Release History DTO

如果不先冻结契约，二期仍会重复一期的典型问题：

- 页面先写了
- 接口后来再改
- DTO 多次漂移
- 联调成本陡增

## 4. 二期总目标

二期完成后，至少应能演示以下闭环：

1. 接入一个 Registry 并查询镜像与 Tag
2. 创建一个服务定义
3. 选择镜像版本并发起一次服务发布
4. 在任务中心查看发布任务步骤与日志
5. 查看服务实例状态
6. 发起一次升级
7. 在升级失败时执行回滚，或手动回滚到历史版本

这条闭环是二期的主验收标准。

## 5. 后端开发路线

## 5.1 阶段一：Registry 模块

### 目标

先补齐发布闭环的镜像来源侧能力。

### 交付内容

- Registry 数据模型
- Registry CRUD
- Registry 连接测试
- 仓库列表
- Tag 列表
- Manifest / Digest 查询
- Registry 凭证通过 Secret 管理
- Registry 操作审计

### 建议接口

- `GET /api/registries`
- `POST /api/registries`
- `GET /api/registries/:id`
- `PATCH /api/registries/:id`
- `DELETE /api/registries/:id`
- `POST /api/registries/:id/test`
- `GET /api/registries/:id/repositories`
- `GET /api/registries/:id/repositories/:repo/tags`
- `GET /api/registries/:id/repositories/:repo/manifests/:reference`

### 风险点

- 认证失败与网络失败要分开报错
- Registry 密码不能落明文
- 删除 Registry 前应检查是否被服务定义引用

### 验收口径

- 可新增一个 Registry
- 可执行连通性测试
- 可查询指定仓库的 Tag 列表
- 可在审计日志中追踪 Registry 关键动作

## 5.2 阶段二：服务定义与实例模型

### 目标

把“待发布对象”从零散的 Docker 操作提升为结构化服务模型。

### 交付内容

- 服务定义模型
- 服务分组 / 标签
- 镜像地址与默认 Tag
- 端口映射
- 环境变量
- 挂载配置
- CPU / 内存限制
- 目标节点或节点选择策略
- 服务实例模型
- 实例列表与实例状态查询

### 建议数据模型

- `services`
- `service_versions`
- `service_instances`
- `service_release_records`

### 建议接口

- `GET /api/services`
- `POST /api/services`
- `GET /api/services/:id`
- `PATCH /api/services/:id`
- `DELETE /api/services/:id`
- `GET /api/services/:id/instances`
- `GET /api/services/:id/releases`

### 风险点

- 服务定义删除前需要引用检查
- 端口、挂载、环境变量需要后端强校验
- 同一服务在同一环境中不应允许无约束重复发布

### 验收口径

- 可创建一条服务定义
- 可查看其关联实例与发布记录
- 参数非法时后端能给出稳定校验错误

## 5.3 阶段三：发布任务引擎

### 目标

让服务发布真正进入任务中心，而不是直接调 Docker 动作。

### 交付内容

- 发布任务类型
- 发布任务步骤
- 发布日志写入
- 简单本地 worker 或统一执行器
- 发布锁
- 失败补偿机制
- 发布完成后写入服务实例
- 发布审计

### 推荐任务步骤

1. 校验输入参数
2. 校验权限
3. 检查目标节点
4. 解析并校验镜像
5. 拉取镜像
6. 创建容器
7. 启动容器
8. 执行健康检查
9. 写入实例记录
10. 记录审计并完成任务

### 建议接口

- `POST /api/services/:id/releases`
- `GET /api/releases/:id`
- `GET /api/releases/:id/logs`

### 风险点

- DB 成功但容器创建失败时需要补偿
- 容器创建成功但实例落库失败时需要补偿
- 同一服务并发发布必须有锁

### 验收口径

- 发起发布时返回 `taskId`
- 任务中心能看到完整步骤和日志
- 失败时能定位到具体失败步骤

## 5.4 阶段四：服务升级与回滚

### 目标

在“首次发布”之上建立版本化运维能力。

### 交付内容

- 版本快照
- 发布历史
- 升级任务
- 回滚任务
- 升级健康检查
- 升级失败回滚
- 手动回滚到历史版本
- 升级与回滚审计

### 建议接口

- `POST /api/services/:id/upgrades`
- `POST /api/services/:id/rollbacks`
- `GET /api/services/:id/history`
- `GET /api/services/:id/versions`

### 推荐策略

- 不允许“先删旧实例再建新实例”
- 升级失败时旧版本应保持可用
- 回滚也必须进入任务中心

### 风险点

- 当前版本识别错误
- 升级过程中实例状态与数据库状态不一致
- 回滚窗口被错误覆盖

### 验收口径

- 可选择目标版本执行升级
- 升级失败后仍能保留旧版本可用
- 可手动回滚到指定历史版本

## 5.5 阶段五：二期后端收口

### 目标

把“能跑通”提升为“能稳定演示和继续扩展”。

### 交付内容

- 二期接口文档补齐
- 发布链路集成测试
- 任务与审计覆盖检查
- 幂等控制
- 部署与联调说明

### 验收口径

- Registry、服务定义、发布、升级、回滚主链路可重复演示
- 关键失败场景有可解释日志
- 不会因重复点击造成重复发布

## 6. 前端开发路线

## 6.1 阶段一：Registry 页面

### 目标

先把二期镜像来源管理能力做成可操作页面。

### 交付内容

- Registry 列表页
- Registry 新增 / 编辑抽屉
- 连接测试按钮
- 仓库列表页
- Tag 列表页
- Secret 选择器
- 区分认证失败 / 网络失败 / 空仓库错误态

### 页面建议

- `RegistryListPage`
- `RegistryDetailPage`

### 验收口径

- 用户可从 UI 新增一个 Registry
- 可完成测试连接
- 可浏览指定仓库的 Tag 列表

## 6.2 阶段二：服务定义页面

### 目标

让服务定义成为独立的前端资源，而不是混入 Docker 节点页面。

### 交付内容

- 服务列表页
- 服务详情页
- 新增 / 编辑服务表单
- 镜像仓库与 Tag 选择器
- 端口配置编辑
- 环境变量编辑
- 挂载配置编辑
- 资源限制编辑
- 目标节点选择

### 推荐交互

- 详情页以“资源详情 + 最近发布 + 当前实例”结构展开
- 危险字段变更前展示摘要确认

### 验收口径

- 可在 UI 中定义一个完整服务
- 表单校验错误能准确映射到字段

## 6.3 阶段三：发布向导

### 目标

形成“提交发布任务”而不是“直接执行危险动作”的前端闭环。

### 交付内容

- 发布向导
- 发布前摘要确认
- 发布参数复核
- 提交后跳转任务详情
- 任务状态联动

### 推荐步骤

1. 选择服务
2. 选择镜像版本
3. 选择目标节点或策略
4. 复核配置摘要
5. 提交发布任务
6. 查看任务进度

### 验收口径

- 可从服务详情直接发起发布
- 提交成功后能稳定进入任务详情
- 发布结果和失败原因对用户可见

## 6.4 阶段四：升级与回滚界面

### 目标

把“版本切换”从任务中心日志阅读提升为明确的业务操作界面。

### 交付内容

- 发布历史页
- 版本差异展示
- 升级向导
- 回滚确认页
- 当前版本 / 目标版本 / 历史版本展示
- 升级失败后的回滚入口

### 推荐交互

- 升级前展示版本差异摘要
- 回滚时强提醒当前生产影响
- 回滚后自动跳转任务详情

### 验收口径

- 用户能明确看到当前版本和目标版本
- 升级失败时能从界面直接进入回滚动作

## 6.5 阶段五：二期前端收口

### 目标

保证二期能力不是“页面拼起来”，而是“稳定可演示”。

### 交付内容

- 权限驱动菜单与按钮控制
- 统一空状态 / 错误状态
- 资源详情页与任务页联动
- 发布历史与任务中心联动
- Playwright 二期主链路冒烟

### 验收口径

- 发布、升级、回滚三条链路可完整演示
- 刷新页面后不丢关键上下文
- 用户能从任务中心追踪任一发布动作

## 7. 前后端协同方式

二期最需要避免的不是“开发慢”，而是“边做边改模型，联调成本失控”。

建议按以下协同方式推进：

### 7.1 先接口，后页面

每一阶段都先由后端产出稳定 DTO 与样例响应，再由前端接页面。

### 7.2 动作统一任务化

发布、升级、回滚必须统一进入任务中心，避免出现：

- 一部分接口返回任务对象
- 一部分接口只返回布尔值
- 一部分页面跳任务详情
- 一部分页面只弹消息

### 7.3 资源页与任务页双入口

每个发布相关动作都应满足：

- 在资源页可发起
- 在任务中心可追踪

### 7.4 风险操作统一确认

以下动作建议统一确认组件与交互口径：

- 提交发布
- 提交升级
- 提交回滚
- 删除 Registry
- 删除服务定义

## 8. 建议排期

如果按当前项目状态估算，二期建议排成 5 个阶段：

1. Registry
2. 服务定义
3. 发布任务
4. 升级回滚
5. 二期收口

若按 1 后端 + 1 名前端推进，建议预留：

- 紧凑排期：6 周
- 稳妥排期：8 周

推荐按 8 周理解更合理，因为当前项目仍有一期收口任务并行存在。

## 9. 最终结论

二期开发路线应当聚焦“服务发布闭环”，而不是继续无序扩张模块面。

最合理的策略是：

1. 先完成一期收口
2. 冻结二期核心 DTO 契约
3. 后端先交付 Registry、服务定义、发布任务、升级回滚
4. 前端按 Registry、服务定义、发布向导、升级回滚界面顺序接入
5. 二期结束标准以“闭环可演示”而不是“页面数量”来判断

如果这条路线执行稳定，三期再进入 Nginx、Jenkins、备份恢复、监控告警，会比现在直接扩模块更加稳妥。
